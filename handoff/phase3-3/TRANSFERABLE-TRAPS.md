## 클래스 B — 정책 의존 해석 오독 (★ 본 실행이 반드시 carry — 자동판정 안 걸림)

| 발견 | 트랩 (이렇게 읽으면 틀린다) | 본 실행 처치 |
|------|------------------------------|--------------|
| **3. 양축 `total_qty`** | 성능 축에 `total_qty=100`을 쓰면 500VU가 수십 ms 내 즉시 매진 → steady 전부 409 → **성공 경로 측정 대상 소멸**. | 정확성 축=100, 성능 축=대용량(1억). 하네스 `PERF_TOTAL_QTY`로 처리(PINS reset 게이트와 한 쌍). |
| **5. fail-fast 한도 미충전** | v4/v5가 공유부하 10s에서 `actual < 100`인 걸 "정합성 실패"로 읽으면 틀림. **대기 큐 부재의 정상 귀결**. | `≤ total`(초과 0)이 합격식. 미달이면 duration↑로 충전 확인. 하네스 FAIL 라벨 ≠ 정합 실패 → 해석으로 닫음(PINS 성공 시그니처). |
| **4. v4 워치독 vs 고정 lease** | v4(워치독 자동갱신)와 v5(고정TTL 30s)는 **비동형**. v4↔v5 성능/지연 차이를 "락 메커니즘 차이"로만 읽으면 "갱신 정책 차이"가 섞인 걸 놓침. | v4=워치독(leaseTime 미지정), v5=고정TTL 30s — 코드·스펙 §8 결정 #4. 비교 시 비동형 명시. |
| **6. fencing 부재** | "compare-del 했으니 안전하다"가 틀림 — compare-del은 *오해제(release 안전)*만 막고, **만료-중간탈취로 인한 두 홀더 동시 점유(mutual exclusion 안전)는 못 막는다 = fencing token 영역**. | (선택) ★스톨 데모로 격리 재현. 3축 서사의 갱신/fencing 축. 어느 분산 락도 fencing은 안 줌 → 스펙 §6 프로덕션 v3 선택 근거. |
| **v3 ≳ v2 반전** | "DB 락이 인메모리 모니터보다 무조건 느리다"는 통념이 이 부하·구성에선 반례. v3 throughput이 v2 동급 이상일 수 있음(DB 대기열 핸드오프의 파이프라이닝 이득). | 방향성만 참고, 본 실행 숫자로 재확인. throughput 버전 간 직접 비교 금지(스펙 Step G). |
| **8. 갱신 스포크 비가시 (3-3-2)** | 정상 부하 throughput으로 "워치독 vs 고정TTL" 효과를 격리하려 하면 실패 — hold ≪ TTL이라 갱신 정책이 안 보이고 **대기 구현(pub/sub vs spin)이 교란**. (bw 실험 자체는 본 실행 미전이.) | 결론만 스펙 Step G에 흡수: 갱신 축은 정상 부하 throughput이 아니라 스톨 조건 정합으로만 드러남(발견6). |
| **★ NEW — 리포트 축 라벨 하드코딩** | `run-coupon-concurrency.sh`의 python 리포트 블록(line 127/143)이 축 라벨을 `"[정확성 축] constant-vus 500 / 10s"`·`"[성능 축] warmup 5s + steady 30s"`로 **고정 문자열** 출력. **데이터값은 실제 env 반영(정상), 설명 라벨만 고정.** 비기본 부하로 돌리면 라벨이 거짓(리허설 스모크 `VUS=20/3s`로 돌렸는데 출력은 "500/10s"로 찍힘 — 실측 확인). **이진 자동판정으론 안 걸림**(스모크가 abort 없이 PASS로 완주, 라벨만 틀림) — 클래스 B 전형. | **본 실행은 기본 부하(500/10s·5s/30s)라 라벨 = 실값 일치 → 무해.** 비기본 env로 측정 시 라벨 무시(데이터값만 신뢰). **하네스 코드 무수정 원칙 유지** — 라벨을 env 변수로 바꾸는 정리는 본 실행/별도 작업으로(번들 단계에서 하네스 수정 금지). |
