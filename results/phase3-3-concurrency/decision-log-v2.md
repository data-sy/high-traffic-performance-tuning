# Phase 3-3 동시성 락 — 의사결정 서사 (ver2: 중립 비교)

> **이 문서는 동일한 phase3-3 결정을 서로 다른 톤으로 서술한 3버전 중 하나다.**
> `ver1=기각 서사` / `ver2=중립 비교` / `ver3=혼합` — 셋 다 톤 비교 기록용으로 보존한다.
> **이 파일은 ver2 — "각자 언제 쓰는지"를 축으로 한 중립 비교다.** 각 선택지를 우열 없이
> "이 조건이면 이게 맞다"로 나열하고, **결론은 독자 판단에 맡긴다.** 이 워크로드의 답(v3)도
> "이 조건에서의 선택"으로만 제시하며 일반적 우열로 격상하지 않는다. 기각 서사는 `ver1`,
> 혼합은 `ver3`을 본다.
>
> **미채택 — 톤 비교 기록용 보존. 채택본은 v3.**
>
> **수치 출처**: 모든 실측은 `results/phase3-3-concurrency/analysis.md`(본 실행 v1~v5 +
> 스톨 데모, 확정·동결본). 락 구조는 `src/main/java/com/project/service/coupon/` 실제 구현.
> 결정 규율·서사 3축은 본 실행 스펙. 추정·외부지식으로 수치를 채우지 않았다.

## 0. 읽는 법

phase3-3의 다섯 버전은 "낮은 게 틀리고 높은 게 맞다"는 사다리가 **아니다**. 각 칸은 **서로 다른
조건에서 각자 정답**인 별개의 도구다. 이 문서는 매 전환점에서 (a) 그 자리의 선택지들 (b) 각
트레이드오프 (c) 어떤 조건이 어느 선택을 부르는지를 나열한다. **"무엇이 최선인가"가 아니라
"언제 무엇인가"**를 묻는다.

세 축을 따라 읽으면 된다 — **정합 범위**(어디까지 같은 결과를 보장하나), **경합 흡수**(직렬화
비용을 어떻게 배출하나), **갱신 정책**(보유 중 만료를 어떻게 다루나). 한 버전이 세 축에서 동시에
움직이므로, 버전 간 단일 숫자 비교는 의미가 무너진다(§규율).

판정 기준만 공통이다: 정합성은 `coupon.issued` 카운터가 아니라 `SELECT COUNT(*) FROM coupon_issue`
(= `actual`) 행 수로 본다.

## 1. 직렬화 수단 — 어떤 조건에 무엇이 맞나 (v1→v2 자리)

임계 구간을 직렬화하는 1차 수단의 후보들. 각자 맞는 자리가 다르다.

| 수단 | 이 조건이면 이게 맞다 | 이 조건이면 부적합 |
|------|----------------------|--------------------|
| **무락** | 경합이 사실상 없거나, 초과가 허용되는 통계적 집계 | 한정 수량 자원에 동시 요청 — 초과가 곧 결함 |
| **낙관적 락 (`@Version` CAS)** | **저경합** — 충돌이 드물어 재시도 비용이 무시할 수준 | **고경합 단일 핫키** — 충돌·재시도가 폭증해 재시도 폭풍 |
| **`ReentrantLock`** | 타임아웃·인터럽트·공정성 등 **세밀한 제어**가 필요 | 제어가 필요 없는 단일 임계 구간 — 복잡도만 추가 |
| **`synchronized`** | 단일 프로세스 + 단일 임계 구간, **단순성이 우선** | 다중 프로세스 정합이 필요 — 모니터가 프로세스 로컬 |

**무락(v1)의 자리**: 이 워크로드는 한정 수량(`total=100`)이라 무락의 조건이 아니다. 실측이
이를 보여준다 — `actual=999`(+899, 10배 초과). 더불어 **보조 지표의 함정**도 기록해 둘 값이다:
`coupon.issued` 카운터는 100으로 캡돼 "한도 지켜진 듯" 보이지만 진실은 행 수 999다. 무락을 쓰는
조건이라면 적어도 정합 판정을 카운터가 아닌 행 수로 해야 한다는 교훈이 여기 있다.

**`synchronized`(v2)의 자리**: 단일 JVM + 단일 임계 구간 + 단순성 우선이라면 맞다.
`CouponIssueServiceV2`가 그 조건의 구현이다 — 단 **트랜잭션 경계와의 순서**가 정확해야 한다.
`@Transactional` 메서드에 `synchronized`를 같이 걸면 프록시 커밋이 모니터 밖에서 일어나 단일
JVM에서도 초과가 난다. 그래서 모니터를 tx 경계 바깥(파사드)에 두고 실제 tx는 별도 빈
`CouponIssueServiceV2Inner`를 프록시 호출한다(락 ⊃ tx). 이 조건을 지켰을 때 실측: `actual=100`
**PASS**, 카운터까지 100으로 진실과 일치.

**경계 조건**: `synchronized`가 정합을 보장하는 범위는 **그 JVM 프로세스 안**까지다. 인스턴스가
둘 이상이면 각자 별도 모니터라 정합이 깨진다(단일 JVM 측정으론 미실증한 **알려진 한계**). 다중
프로세스 정합이 요구 조건에 들어오면, 다음 자리로 넘어간다.

## 2. 공유 직렬화 좌표 — 어떤 조건에 무엇이 맞나 (v2→v3 자리)

"다중 인스턴스 정합"이 요구 조건이 되면, 모든 인스턴스가 공유하는 좌표가 필요하다. 후보들.

| 수단 | 이 조건이면 이게 맞다 | 이 조건이면 부적합 |
|------|----------------------|--------------------|
| **DB 유니크 제약** | 막을 대상이 **"같은 키의 중복"** (같은 사용자 중복 발급 등) | 막을 대상이 **서로 다른 주체의 초과** — 유니크가 닿지 않음 |
| **낙관적 락 (`version`+재시도)** | 공유 + **저경합** | 공유 + 고경합 단일 핫키 — 재시도 폭풍 |
| **비관적 행 락 (`SELECT FOR UPDATE`)** | 공유 + **고경합** + 보호 대상이 DB 안 | 보호 대상이 DB 밖 / 락 대기로 인한 풀 점유가 치명적 |

이 워크로드의 조건: 막을 대상은 **서로 다른** 다수 사용자의 초과 발급(유니크 제약이 닿지 않음)
+ 단일 핫키 고경합(낙관적 락 부적합) + 보호 대상이 DB 안. 세 조건이 비관적 행 락을 가리킨다.

**비관적 행 락(v3)의 자리**: `CouponIssueServiceV3`은 v2와 **정반대 구조**다 — 행 락은 커밋 시
풀리므로 락 획득·검사·발급을 **하나의 `@Transactional` 안**에서 한다(단일 빈, 파사드 없음).
`findByIdForUpdate`로 행 락을 잡은 후 검사/발급한다. 실측: `actual=100` **PASS**.

**이 선택에 딸려오는 비용 — 풀 압박**: FOR UPDATE가 커넥션을 쥔 채 행 락을 대기 → 대기 요청이
커넥션 점유. 실측 HikariPool **active=10/10(포화), pending=189, idle=0**. 이는 비관적 행 락을
선택할 때 **함께 받아들이는 특성**이지 결함이 아니다. 측정·튜닝(풀·타임아웃 핀) 대상이다.

**이 핀·부하에서의 관찰(음성 결과)**: ⓐ(풀 고갈)/ⓑ(행락 타임아웃) 503 분류는 배선·풀 포화까지
검증됐으나 **타임아웃이 안 나** 503=0이었다. 임계 구간이 짧아(수 ms) 커넥션이 빠르게 순환 → 어느
대기자도 connTO 30s를, 어느 행락 대기도 50s를 안 넘겼다. 해석: **이 조건에서 DB 행 락은 경합을
거절(503)이 아니라 지연(성공 p95 2.6s)으로 흡수한다.** 같은 비관적 행 락이라도 임계 구간 길이·
타임아웃 핀이 다른 조건에선 503이 날 수 있다 — 이 음성은 "이 조건에서의 관찰"이다.

## 3. 분산 락 — 어떤 조건에 무엇이 맞나 (v3→v4 자리)

직렬화 좌표를 DB 밖(Redis)으로 더 빼는 선택. 분산 락이 v3 대비 **더해주는 것**과 **함께 떠안는
것**을 조건별로 갈라 둔다.

| 축 | DB 행 락 (v3) | Redis 분산 락 (v4/v5) |
|----|---------------|----------------------|
| 보호 대상이 **DB 안** | 락↔데이터 동일 시스템 — 원자적 | 락↔데이터 분리 — fencing 공백 발생 |
| 보호 대상이 **DB 밖**(외부 API 멱등성 등) | 보호 불가(DB 트랜잭션 밖이라 닿지 않음) | **적합** — 임의 비-DB 임계 구간 보호 |
| DB 부하 분리 필요 | 락 경합이 DB·커넥션 풀에 실림 | 락 경합을 DB 밖으로 분리 |
| 인프라 비용 | 추가 0 | Redis SPOF·운영 추가 |
| 다중 인스턴스 정합 | 공유 DB 행 락으로 이미 확보 | 공유 Redis로 확보 (v3 대비 *범위* 추가는 아님) |

**선택의 분기점은 "보호 대상이 어디 있나"다.** 보호 대상이 DB 안이면 분산 락은 락을 데이터에서
떼어내 공백을 여는 쪽이고, DB 밖이면 분산 락만이 닿는다. DB 부하 분리가 절실하거나 Redis가 이미
핵심 경로로 깔려 있으면 그 무게가 분산 락 쪽으로 기운다.

두 구현 모두 정합은 회복한다(둘 다 fail-fast):

- **v4 — Redisson `RLock`**: 파사드(락 ⊃ tx), `tryLock(0, …)` fail-fast, leaseTime 미지정 →
  **워치독 자동 갱신**. 가드 둘(미획득 unlock 금지, RedisException을 단일 ⓒ로). 실측: 정합
  `≤ total`(초과 0); 10s `actual=62`(대기 큐 없는 fail-fast의 정상 미충전), 90s `actual=100`
  수렴. 503 ⓒ 249,563, 미분류 0, 거절률 99.9%.
- **v5 — 커스텀 `SET NX` + Lua**: v4와 동형 파사드, **고정 TTL 30s 무갱신**. 락 전용
  `StringRedisTemplate`로 직렬화 함정(JSON 따옴표 → Lua 비교 실패 → release 불가) 회피.
  실측: `actual=100` **PASS**, 503 ⓒ 281,977, 미분류 0, 거절률 99.7%.

> **거절률 99%대의 조건 한정**: 이는 **단일 핫키 + 즉시실패**의 귀결이지 분산 락 일반의 성질이
> 아니다. 키가 분산되거나 짧은 대기를 주면 달라진다.

## 4. 갱신 정책 — 어떤 조건에 무엇이 맞나 (v4 vs v5 자리)

분산 락 보유 중 만료를 다루는 두 방식.

| 정책 | 이 조건이면 이게 맞다 | 실패 모드 |
|------|----------------------|-----------|
| **워치독 자동 갱신** (v4) | hold 시간이 가변·예측 불가 — 고정 TTL을 넘길 위험 | 클라이언트 측 갱신 로직 복잡도 |
| **고정 TTL 무갱신** (v5) | hold가 짧고 **TTL을 worst-case보다 충분히 크게** 잡을 수 있음 | TTL 조기 만료 시 만료-중간탈취 |

**정상 부하로는 둘을 가를 수 없다(발견8)**: hold(수 ms)가 TTL(30s)보다 압도적으로 짧아, 고정
TTL이 임계 구간 중간에 만료될 일이 정상 부하에선 없다 → 워치독이 막아줄 사건이 안 생긴다.
따라서 v5(28.4/s, 성공 p95 106ms)와 v4(6.3/s, 성공 p95 418ms)의 throughput 차이는 **갱신 정책이
아니라 대기/락 구현 아티팩트**(Redisson pub/sub+워치독 스케줄링 vs 커스텀 경량 SET NX)다. 어느
쪽이 빠르다는 인과를 **세우지 않는다.** 두 정책의 실제 차이는 hold>TTL인 스톨 조건에서만 드러난다
(§5).

## 5. fencing — 분산 락 공통의 경계 (스톨 데모)

`CouponStallDemoService`로 만료-중간탈취를 인위 주입한 통제 실험. `total_qty=1`, **`ttl=1s < stall=3s`**.
스톨 중 보유 TTL이 만료되면 다른 홀더가 만료된 락을 훔쳐 같이 발급한다.

- **결과**: A `released=false`(compare-del이 자기 토큰 아님을 보고 **해제 거부 = 오해제 차단 ✓**)
  인데도 **`actual=2 > total=1`**(user 9001·9002 둘 다 발급) = **동시 점유 발생 ✗**.

**중립적 사실로서**: 안전한 release(오해제 차단)와 상호배제(동시 점유 차단)는 **별개**다.
compare-del은 전자만 준다. 후자는 **fencing token(자원 측 단조번호 검증) 없이는 어느 분산 락도
못 준다** — 워치독(v4)도 GC pause/네트워크 단절 앞에선 동일하다. 즉 **갱신 정책 선택과 무관하게,
Redis 분산 락은 fencing-safe하지 않다.** (이 초과는 데모의 통제 산물 — 정상 v4/v5는 초과 0.)

대조적으로, **락과 데이터가 같은 트랜잭션 안에 있는 v3는 만료-중간탈취 자체가 불가**하므로
이 공백이 구조적으로 없다. 이것은 두 선택지의 우열이 아니라 **메커니즘의 차이**다 — 락을
데이터에서 떼어냈는지 아닌지.

## 6. 종합 — 조건이 선택을 부른다 (독자 판단의 몫)

세 축을 한 표로. 각 칸은 "더 좋다/나쁘다"가 아니라 **"이 조건에 맞다"**로 읽는다.

| | v1 | v2 | v3 | v4 | v5 |
|---|----|----|----|----|----|
| 정합 actual (total=100) | **999** | 100 | 100 | ≤total ✓ | 100 |
| 정합 범위 | 없음 | 단일 JVM | 다중(공유 DB행) | 다중(외부 Redis) | 다중(외부 Redis) |
| 경합 흡수 | 무시(초과) | park | DB큐(지연) | fail-fast(거절) | fail-fast(거절) |
| 갱신 정책 | — | — | — | 워치독 | 고정 30s |
| fencing | — | — | 구조적 무공백 | 부재 | 부재 |
| 맞는 조건 | 초과 허용 집계 | 단일 JVM·단순성 | 공유·고경합·DB내 보호 | 비-DB 구간·부하분리 | 좌동(원리 노출) |

**버전 간 단일 숫자 비교는 하지 않는다(규율)**: throughput·지연·503율은 경합 전략이 버전마다
달라(park/DB큐/fail-fast) 같은 컬럼이라도 의미가 다르다. v3 throughput(317.5/s)이 v2(263.6/s)를
웃돈 것, v5가 v4를 웃돈 것은 모두 **관측·미증명·단일 런**이다 — 경합을 통일하면 격차가 어떻게
수렴하는지는 **별도 통제 실험에서 경합을 고정해 확인**했고, 원본 사다리에선 직접 비교하지 않으며
그 수치도 끌어오지 않는다. 각 throughput은 그 버전 정책의 자체 특성으로만 읽는다.

**이 워크로드의 답**: 조건이 — 보호 대상이 DB 안 + 단일 핫키 고경합 + Redis 부하 분리 불요 +
fencing 공백을 열지 않음을 원함 — 이라면, 표는 **v3**를 가리킨다. 정규 발급 경로
(`POST /api/coupons/issue`)는 v3에 배선돼 있다. **단 이것은 "v3가 일반적으로 우월하다"는 주장이
