## ★ 확정 방향 (2026-06-09 사람·컨설턴트 결정 반영)

> 후보 풀(앵글 A~E)은 채굴 라이브러리로 그대로 둔다. 아래는 그 위에서 **사람이 고른 채택 방향**이다.

**결정 요약**
- **결론은 v3(DB 비관적 행 락) 유지** — Redis 분산락으로 돌리지 않는다.
- **서사는 진행형(시도1→2→3)으로 재구성**하되 착지는 v3. (포폴 블록 한정 — 이력서는 한 줄이라 진행형 영향 없음)
- **다중서버 실증은 백로그**(ROADMAP `Later` → 보강#1). 지금 돌리지 않으며, 결론·서사는 그것 없이도 v3로 닫혀 있다.

**왜 Redis로 안 돌리는가 (1줄 방어)**: 다중서버를 띄우면 깨지는 건 **v2(synchronized) 하나**고 v3는 이미 다중 인스턴스 정합(공유 DB 행) → 다중서버는 "공유 좌표 필요"까지만 증명하지 "Redis 필수"를 증명하지 않는다. Redis 착지는 ① 동결된 analysis.md/회고/README와 모순 ② 자기 반증 차별점을 버리고 제네릭 사다리로 추락 ③ 스톨 데모(actual=2)가 본인을 반박 → **방어 불가**.

### 잠근 이력서 줄 (A-1 채택 — 기존 `resume_item_6`과 정합, 별도 수정 불필요)
> 한정 수량 쿠폰 동시 발급에서 무락 경쟁으로 **초과발급(actual=999, +899, 10배) 발생 → 락 사다리 v1~v5(무락→synchronized→DB 행 락→Redisson→커스텀 SET NX)를 끝까지 구현·측정하고 워크로드 적합성을 근거로 DB 비관적 행 락(v3) 채택**. 초과발급 **999 → 0**.

- 포폴/면접 헤드라인 보강용으로 **B-1(자기 반증)·D-2(fencing 스톨 데모)** 동반 권장.

### 진행형 포폴 블록 초안 (시도1→2→3, v3 착지)

> **제목**: 쿠폰 한정 발매 동시성 — synchronized → DB 행 락 → 분산락까지 가보고 내린 선택

**문제.** 한정 수량(total=100) 쿠폰을 다수가 동시 요청하면 check-then-act(`issued<total`→`issued++`)가 비원자라 stale `issued`를 동시에 읽고 통과 → 무락 기준선에서 **actual=999(+899, 10배 초과)**. 정합 판정은 lost update로 부정확한 카운터(`coupon.issued`=100)가 아니라 **`coupon_issue` 행 수**를 단일 진실 소스로 삼았다.

**시도1 — synchronized (JVM 락).** 모니터를 tx 경계 밖(파사드)에 두고 실제 tx는 별도 빈으로 분리(락 ⊃ tx, 프록시 함정 회피)해 **actual=100(실측)** 회복. **한계**: 모니터가 JVM 로컬이라 다중 인스턴스에선 서버마다 별도 락 → 깨짐. ⚠️ 이 붕괴는 **개념적 한계이며 단일 JVM 측정으론 미실증**(다중서버 실증은 ROADMAP 백로그). → "JVM 로컬 좌표로는 안 되고 **공유 좌표**가 필요"가 다음 칸의 동기.

**시도2 — DB 비관적 행 락 (SELECT FOR UPDATE).** 락 획득·검사·발급을 **하나의 `@Transactional`** 안에서. 락↔데이터가 같은 DB·같은 트랜잭션이라 원자적이고, 직렬화 좌표가 JVM 로컬 → **공유 DB 행**으로 이동해 다중 인스턴스 정합도 이미 확보(개념적; 단일 JVM 미실증). **actual=100(실측)**. 비용: FOR UPDATE가 커넥션을 쥔 채 행 락 대기 → 풀 압박(HikariPool **active 10/10, pending 189**, 실측) — 측정·튜닝 가능하고 본 규모서 수용.

**시도3 — Redis 분산락 (Redisson RLock + 커스텀 SET NX/Lua).** "분산락이 v3보다 더 주는 게 있나"를 확인하려 **끝까지 구현**. 둘 다 초과 0 회복. 그러나 스톨 데모(`ttl=1s < stall=3s`)로 만료-중간탈취를 주입하니 **오해제는 거부됐는데도(released=false) actual=2 > total=1** — 동시 점유 발생. **안전한 release ≠ 상호배제**이고, 후자는 **fencing token 없이는 어느 분산락도 못 막는다**(워치독도 GC pause/네트워크 단절엔 동일). 락↔데이터를 다른 시스템으로 분리한 대가다.

**착지 — v3 채택.** 이 워크로드의 임계 구간이 곧 DB 쓰기라 보호 대상(coupon 행)이 **이미 DB 안**에 있다. v3는 락과 데이터가 같은 트랜잭션이라 만료-중간탈취 자체가 불가 → **fencing 공백이 구조적으로 없다.** 그래서 v3는 "충분"이 아니라 이 워크로드에선 **더 안전**하다. Redis 분산락이 본래 맞는 자리는 보호 대상이 **DB 밖**(외부 API 멱등성, 비-DB 자원)일 때. "왜 트렌드(분산락)를 안 썼나"의 답은 트렌드 무지가 아니라 **워크로드 적합성 판단**이다.

**메타(차별점).** 시도2의 throughput(317.5/s)이 시도1(263.6/s)보다 높게 나와 "DB 락이 더 빠르다" 헤드라인이 손에 잡혔으나, 경합 전략이 함께 움직인 **confound로 판정해 채택하지 않았다** — 통제 재실험에서 격차가 작은 락-위치 비용으로 수렴(near-parity)함을 확인하고 throughput 막대그래프를 한 장도 그리지 않았다. 잘 나온 자기 측정을 스스로 뒤집은 측정 규율이 이 작업의 진짜 차별점이다.

> ⚠️ **정직성 핀**: 시도1의 다중서버 붕괴와 시도2의 다중 인스턴스 정합은 **현재 개념적·단일 JVM 미실증**이다. "다중서버서 깨짐을 실측" 같은 표현은 **백로그(보강#1) 실행 전엔 쓰지 않는다.** 실험을 돌리면 v2 붕괴·v3 유지가 *실측*으로 승격되고, 그때 이 꼬리표를 떼고 "다중 인스턴스 정합 실증"으로 올린다. 이 실험은 v3를 **강화**한다(반증 아님).

## 앵글 A — 의사결정 · 워크로드 적합성

### A-1. 사다리 끝까지 구현하고도 워크로드 적합성으로 v3 채택 (대표)
1. **이력서용**: 한정 수량 쿠폰 동시 발급의 동시성 제어 수단을 정하며 **락 사다리 v1~v5(무락→synchronized→DB 행 락→Redisson→커스텀 SET NX)를 끝까지 구현·측정하고 워크로드 적합성을 근거로 DB 비관적 행 락(v3)을 채택**, 초과발급 **999 → 0**.
2. **포폴용**: 쿠폰은 `total_qty=100`의 한정 자원이라 동시 요청 시 초과발급이 정합 붕괴로 직결된다. "제일 고급 기법을 고른다"가 아니라 각 칸이 *서로 다른 조건에서 각자 정답*인 별개 도구임을 전제로 사다리를 끝까지 밟았다. 분산 락이 v3 대비 무엇을 더(혹은 못) 주는지 직접 구현해 확인하지 않고는 v3를 정답이라 부를 수 없었기 때문이다. 결론은 이 워크로드의 임계 구간이 곧 DB 쓰기이므로 v3 채택.
3. **출처**: analysis.md §종합비교 표(v1 actual=999 → v2~v5 초과 0), §6 프로덕션 배선; decision-log-v3.md §6; 코드 `CouponIssueServiceV1..V5.java` 5종 실재.
4. **면접 방어**: "왜 끝까지 다 구현했나, 오버엔지니어링 아닌가?" → Y. 보고서가 "직접 구현해 확인하지 않고는 v3를 정답이라 부를 수 없었다"로 동기를 명시(report §2, decision-log-v3 §0).
5. **정직성 플래그**: 없음. (단 "채택=성능 우위"로 읽히지 않게 결과는 '초과 0'(정합)으로만 표기.)

### A-2. 락↔데이터 동치(원자성)를 채택 핵심 근거로
1. **이력서용**: 보호 대상(coupon 행)이 이미 DB 안인 워크로드에서 **락과 데이터를 같은 트랜잭션에 두는 DB 행 락을 선택**해, 락을 외부(Redis)로 분리할 때 생기는 fencing 공백을 구조적으로 제거.
2. **포폴용**: v3는 FOR UPDATE 행 락과 데이터가 같은 DB·같은 트랜잭션 안에 있어 원자적이고, 락이 커밋 시 풀리므로 만료-중간탈취 자체가 불가능하다. 락을 Redis로 빼는 순간 락↔데이터가 다른 시스템으로 분리되며 그 공백이 열린다. 그래서 v3는 "충분"한 게 아니라 **이 워크로드에선 더 안전**하다.
3. **출처**: analysis.md §6 핵심 근거("락↔데이터 동치"), 한계 절; report §5 구조도·§6; decision-log-v3 §6 근거X; 코드 `CouponIssueServiceV3.java`(단일 `@Transactional` 안 락·검사·발급).
4. **면접 방어**: "fencing 공백이 없다는 걸 어떻게 단정하나?" → Y. 락이 커밋과 동시에 해제되는 트랜잭션 경계 구조(코드 33–45행)와 스톨 데모 대조(actual=2 vs v3 구조적 무공백)로 받침.
5. **정직성 플래그**: 없음. (구조적 논증이라 단일 JVM 측정 한계와 무관.)

### A-3. "트렌드(분산 락)를 안 쓴 이유" = 워크로드 적합성 판단
1. **이력서용**: 분산 락이 트렌드인 상황에서 **"왜 안 썼나"를 트렌드 무지가 아닌 워크로드 적합성으로 답할 수 있도록, Redis 분산 락이 본래 맞는 자리(보호 대상이 DB 밖)와 본 워크로드의 차이를 분석**해 채택을 정당화.
2. **포폴용**: Redis 분산 락은 보호 대상이 DB 밖(외부 API 멱등성, 비-DB 자원)일 때 의미가 있다. 본 워크로드는 보호 대상이 DB 행이라 락을 데이터에서 떼어내는 것 자체가 역효과(fencing 공백 + 단일 Redis SPOF)다. 맥락이 바뀌면(Redis가 핵심 캐시로 이미 깔림 + DB 부하 분리 절실 + 비-DB 임계 구간) v4로 이전한다는 반대 조건까지 명시했다.
3. **출처**: analysis.md §6("왜 분산 락을 안 썼나" 단락 + 맥락 전환 조건); report §6 표(선택지별 더해주는 것/떠안는 것); decision-log-v3 §6 "이 결정의 범위와 반대 조건".
4. **면접 방어**: "그럼 분산 락은 언제 쓰나?" → Y. "보호 대상이 DB 밖일 때"로 반대 조건이 문서에 명시.
5. **정직성 플래그**: 없음.

### A-4. v3가 다중 인스턴스 정합을 이미 준다 (Redis≠스케일아웃 전제) — 한계 동반 필수
1. **이력서용**: **공유 DB 행 락은 인스턴스를 늘려도 모두 같은 행 락을 경유하므로 다중 인스턴스 정합이 Redis 없이 이미 확보됨을 근거로**, "스케일아웃하려면 분산 락"이라는 통념을 반박.
2. **포폴용**: v4/v5가 v3를 넘어 더해주는 것은 정합의 *범위*가 아니라 *비-DB 임계 구간 보호*뿐이다. 다만 이 다중 인스턴스 정합은 공유 DB 행 락의 **개념적 보장이며 단일 JVM 측정으로는 미실증**이다 — 다음 검증으로 Docker Compose N-인스턴스 + LB + 공유 Redis 실측을 남겨뒀다.
3. **출처**: analysis.md §6 "⚠️ 오독 방지" + 한계 절("다중 인스턴스 미검증 = 알려진 한계, 다음 후보"); report §6·§8.
4. **면접 방어**: "그 정합을 측정으로 보였나?" → **부분 Y**. 개념적 보장은 구조로 받치되, 실측은 미수행임을 문서가 한계로 정직하게 표기 → 방어는 "한계를 안다"로.
5. **정직성 플래그**: ⚠️ 미실증. 반드시 "개념적 보장·단일 JVM 미실증" 꼬리표와 함께 써야 함. 단독 '입증' 주장 금지.

## 앵글 B — 측정 규율 · 자기 반증 [헤드라인]

### B-1. 잘 나온 자기 벤치마크를 통제 재실험으로 스스로 반증 (헤드라인 대표)
1. **이력서용**: throughput에서 v3(DB 락) > v2(애플리케이션 락)가 나와 "DB 락이 더 빠르다" 헤드라인이 잡혔으나, **이를 채택하지 않고 경합 전략이 함께 움직인 confound로 판정 → 통제 재실험으로 격차가 작은 락-위치 비용으로 수렴함을 확인하고 throughput 헤드라인을 폐기**.
2. **포폴용**: 버전 간 throughput 격차(v3 317.5/s > v2 263.6/s, v5 28.4/s > v4 6.3/s)의 지배 변수는 락 위치가 아니라 경합 전략이 같이 움직인 교란이었다(v1·v2·v3=대기 흡수, v4·v5=fail-fast 거절). 경합을 유한대기로 통일한 별도 통제 재실험에서 격차가 작은 단조 락-위치 비용으로 수렴함을 확인하고, v3>v2·v5>v4 반전은 전부 '관측·미증명·단일 런'으로만 적었다. 잘 나온 자기 측정을 스스로 뒤집은 것이 이 작업의 핵심이다.
3. **출처**: analysis.md §종합비교 표(throughput 행) + "★ throughput 버전 간 직접 비교 금지 — 그 이유"; report §9-(2); decision-log-v3 §6 "throughput은 근거로 쓰지 않았다".
4. **면접 방어**: "그럼 v3>v2가 진짜로 거짓인가?" → Y. confound임을 통제 재실험으로 확인했고, 원 사다리엔 그 수치를 끌어오지 않았다고 문서가 명시(report §9-(2), §8 경합 상호작용 실험).
5. **정직성 플래그**: ⚠️ 통제 재실험 자체의 수치는 본 사다리 analysis.md에 없음 — '수렴했다'는 정성 결론만 인용 가능, 구체 수렴 수치 인용 금지(출처: 별도 실험, 본 스코프 밖).

### B-2. throughput 버전 간 직접 비교 금지 규율을 스스로 부과
1. **이력서용**: 동일 컬럼이라도 경합 전략(park/DB큐/fail-fast)이 달라 의미가 다른 점을 근거로 **throughput·지연·503율의 버전 간 직접 비교를 금지하는 규율을 스스로 부과하고, 비교 합법 축(정합 actual)과 정책 관찰치(503 거절률)만 시각화**.
2. **포폴용**: throughput 막대그래프를 한 장도 그리지 않은 것이 이 규율의 시각적 귀결이다. 같은 503이라도 v3의 0%는 "지연으로 흡수", v4/v5의 ~100%는 "단일 핫키+즉시실패의 귀결"이라 의미가 다르다. 비교가 정당한 축(초과발급 차단 여부, 이진 질문)만 직접 비교했다.
3. **출처**: analysis.md §종합비교 ⚠️ 헤더 + 측정범위 Note(Step G); report §0 ⚠️·§4.5·§9-(2)("막대그래프 한 장도 그리지 않은 게…").
4. **면접 방어**: "그럼 성능은 어떻게 비교하나?" → Y. outcome별 분리 + 버전 내 정책 관찰치로 읽는다는 방법을 문서가 제시.
5. **정직성 플래그**: 없음.

### B-3. 통제변수 핀이 비교 유효성을 보존 (선결정 방지)
1. **이력서용**: v1~v5에 HikariCP 풀(10)·connection-timeout(30s)·Tomcat threads(200)·MySQL innodb_lock_wait_timeout(50s)·격리수준(RR)을 **공통 핀으로 고정해, "v3=커넥션 고갈" 같은 간판이 측정이 아니라 두 기본값 대소관계로 선결정되는 것을 차단**.
2. **포폴용**: 통제변수는 값이 정답이 아니라 "전 버전 동일"이 핵심이었다. 이 핀이 없었다면 503 ⓐ/ⓑ 비율 같은 결과가 *측정*이 아니라 pool·timeout 두 값의 대소로 미리 정해졌을 것이다.
3. **출처**: analysis.md §통제변수 표(5종 핀); report §3 표·§9-(1).

5. **정직성 플래그**: 없음.

### B-4. 핀 검증의 정직한 비대칭 (전수 실측이 아님을 명시)
1. **이력서용**: 모든 핀을 실측했다고 과장하지 않고 **검증으로 구별할 시나리오가 있는 핀(pool은 negative test, innodb·RR은 런타임 assert)만 결정적으로 검증하고, 결과가 어차피 동일한 Tomcat 핀은 '무해 미검증'으로 정직하게 기록**.
2. **포폴용**: pool은 yml을 비기본값 11로 띄워 실제 Hikari 메트릭이 11로 바뀜을 확인 후 10 복원해 바인딩 경로를 증명했다. innodb·RR은 하네스가 매 측정 시작에 실측·대조해 불일치면 abort한다. Tomcat은 값이 프레임워크 기본값과 같고 역할이 "충분히 큰 값"이라 핀이 먹든 기본값이든 결과가 같아 구별할 시나리오가 없어 검증 동기가 없었다 — 이 비대칭을 숨기지 않고 방법론으로 기록했다.
3. **출처**: analysis.md §핀 검증 방식(정직한 비대칭) 전체; report §3 표 + 본문.
4. **면접 방어**: "그럼 Tomcat이 안 먹었으면 결과가 틀린 거 아닌가?" → Y. pool/connTO의 침묵형 위험(안 먹으면 ⓐ/ⓑ 비율 변동)이 Tomcat엔 적용 안 됨을 문서가 논증.
5. **정직성 플래그**: 없음(이 후보 자체가 정직성을 보이는 후보).

### B-5. 측정 함정을 클래스 A/B로 분류해 자동 판정이 못 거르는 오독을 차단
1. **이력서용**: 측정 함정을 **환경 의존(클래스 A: assert·negative test로 차단)과 정책 의존 해석 오독(클래스 B: 도구로 못 막고 해석으로만 닫힘)으로 분류해**, 이진 자동 판정이 기계적으로 FAIL로 찍는 정상 결과(v4 fail-fast 미충전 actual=62)를 오판하지 않도록 함.
2. **포폴용**: 하네스의 이진 PASS/FAIL은 v4의 10s actual=62를 기계적으로 FAIL로 찍지만, 그건 정합 실패가 아니라 대기 큐 부재의 fail-fast 정상 귀결이고 duration을 90s로 늘리면 actual=100으로 수렴한다. 클래스 A는 도구로 막을 수 있어도 클래스 B는 해석으로만 닫힌다는 구분이 핵심이었다.
3. **출처**: analysis.md v4 §해석(62→100 수렴), §종합비교 각주¹; report §9-(3) 클래스 A/B 표.
4. **면접 방어**: "actual=62면 한도 미달인데 어떻게 PASS인가?" → Y. 합격식이 `≤total`(초과 0)이고 90s 충전 시 100 수렴함을 문서가 닫음.
5. **정직성 플래그**: 없음.

## 앵글 D — 정확성 · 안전성

### D-1. 무락 초과발급 999 → 0, 정합을 카운터가 아닌 행 수로 진실 판정 (대표)
1. **이력서용**: 한정 수량 쿠폰 동시 발급에서 무락 경쟁으로 **초과발급(actual=999, +899, 10배) 발생 → 락으로 초과 0 회복**. 정합 판정을 lost update로 부정확한 `coupon.issued` 카운터가 아니라 **`coupon_issue` 행 수를 단일 진실 소스로 삼아** 검증.
2. **포폴용**: v1에서 카운터(`coupon.issued`)는 100으로 천장에 캡돼 "한도 지켜진 듯" 보였지만(lost update), 실제 발급 행 수는 999였다. 카운터만 믿으면 "100 발급, 한도 준수"로 오판한다. 그래서 정합 판정의 단일 진실 소스를 `SELECT COUNT(*) FROM coupon_issue`로 고정했다.
3. **출처**: analysis.md v1 §결과(counter=100 vs actual=999) + §해석("counter vs actual 갈림 = lost update 증거"); report §3·§4.1.
4. **면접 방어**: "왜 카운터가 거짓말을 하나?" → Y. check-then-act 비원자성과 lost update 메커니즘을 문서가 설명(단, 메커니즘 자체는 지식체크용).
5. **정직성 플래그**: 없음. (단 999는 '재현된 기준선'이지 '내가 만든 버그'가 아님 — '무락의 정상 귀결'로 표기.)

### D-2. fencing 부재를 스톨 데모로 실증 (actual=2 > total=1)
1. **이력서용**: 분산 락 스톨 데모에서 만료-중간탈취를 주입해 **오해제는 거부됐는데도(release=false) actual=2 > total=1이 발생함을 실측**, "안전한 release ≠ 상호배제"를 증거로 fencing 부재를 입증.
2. **포폴용**: `ttl=1s < stall=3s`로 보유 중 TTL이 만료되게 통제하니, A의 compare-del이 자기 토큰 아님을 보고 해제를 거부(released=false)했음에도 B가 만료된 락을 훔쳐 들어가 둘 다 발급(actual=2)됐다. 만료-중간탈취로 인한 동시 점유는 fencing token(자원 측 단조번호 검증) 없이는 어느 분산 락도 못 막는다 — v4 워치독도 GC pause/네트워크 단절엔 동일한 한계다.
3. **출처**: analysis.md v5 §스톨 데모(A released=false, actual=2>total=1); report §4.4; 코드 `CouponStallDemoService.java`(ttl<stall 주입, finally unlock).
4. **면접 방어**: "워치독(v4) 쓰면 막히지 않나?" → Y. 워치독도 GC pause/네트워크 단절엔 동일 한계임을 문서가 명시.
5. **정직성 플래그**: ⚠️ "데모의 통제 산물 — 정상 v4/v5는 초과 0"을 반드시 동반. "분산 락은 항상 초과발급한다"로 오독되면 폐기.

### D-3. 프록시 함정 회피를 actual=100으로 실증 (락 ⊃ tx) — 면접 지식체크용
1. **이력서용(보류 권장)**: synchronized(v2)에서 **@Transactional 메서드에 락을 같이 걸면 커밋이 모니터 밖에서 일어나 단일 JVM에서도 초과가 나는 프록시 함정을, 모니터를 tx 경계 밖(파사드)에 두고 실제 tx를 별도 빈으로 분리(락 ⊃ tx)해 회피**하고 actual=100으로 검증.
2. **포폴용**: 같은 빈 자기호출이면 커밋이 모니터 밖으로 새 lost update가 재발해 actual>100이 나야 한다. actual=100(PASS)이 분리가 런타임에 올바로 먹었다는 결정적 증거다. v2가 락 ⊃ tx(파사드), v3가 tx ⊃ 락(단일 빈)으로 정반대 구조인 것도 락의 해제 시점 차이에서 나온다.
3. **출처**: analysis.md v2 §구현·§해석(프록시 함정 회피 실증, actual=100); 코드 `CouponIssueServiceV2.java`(synchronized 밖 + inner 별도 빈), `CouponIssueServiceV2Inner.java`, 대조 `CouponIssueServiceV3.java`(단일 @Transactional).
4. **면접 방어**: "왜 v2는 별도 빈인데 v3는 단일 빈인가?" → Y. 모니터 해제 시점 vs 행 락 커밋 해제 시점 차이로 문서가 설명.
5. **정직성 플래그**: ⚠️ 지엽 트러블슈팅 — **헤드라인 금지, 면접 지식체크용**. 다만 '락 ⊃ tx / tx ⊃ 락 구조 대비'는 깊이 어필로 면접에서 강함.

### D-4. tx/락 순서·503 오염 방지 가드 — 면접 지식체크용
1. **이력서용(보류 권장)**: **풀 고갈(ⓐ)이 tx-begin/첫 쿼리에서 날 수 있어 503 분류를 @Transactional 밖(컨트롤러 경계)에서 잡고, v3 경로에만 적용해 v1/v2의 무락 풀 누수가 ⓐ로 위장되는 오염을 차단**.
2. **포폴용**: 분류기를 트랜잭션 안에 두면 eager/delayed 커넥션 획득 중 일부를 놓친다. 또 분류기를 전역에 걸면 v1/v2의 풀 누수 500이 ⓐ(spurious POOL_TIMEOUT)로 오염된다 — 그래서 v3 경로 전용으로 한정했다. v4/v5는 미획득 시 unlock을 호출하지 않아(IllegalMonitorStateException→500 오염 방지) 비슷한 가드를 뒀다.
3. **출처**: analysis.md v3 §구현 요지(503 분류 컨트롤러 경계, v1/v2 미적용), v4 §구현(미획득 unlock 금지 가드); 코드 `CouponDbExceptionClassifier.java`(예외 체인 순회, 미분류→원예외→500).
4. **면접 방어**: "왜 컨트롤러 경계에서 분류하나?" → Y. ⓐ가 tx 밖에서 날 수 있음을 코드 주석·문서가 설명.
5. **정직성 플래그**: ⚠️ 지엽 트러블슈팅 — **헤드라인 금지, 면접 지식체크용**.

### E-3. 503 서브분류 ⓐ/ⓑ/ⓒ + 미분류 0 검증
1. **이력서용**: 503을 단일 코드로 뭉뚱그리지 않고 **풀 고갈(ⓐ POOL_TIMEOUT)·행락 타임아웃(ⓑ LOCK_WAIT_TIMEOUT, MySQL 1205)·락 거절(ⓒ LOCK_NOT_ACQUIRED)로 예외 체인 실측 분류**하고, v4/v5에서 249,563·281,977건이 ⓒ로 라우팅되며 미분류 0임을 검증.
2. **포폴용**: 분류기는 예외 체인을 순회해 SQLTransientConnectionException은 ⓐ, errorCode 1205는 ⓑ로 잡고, 미분류면 원예외를 그대로 반환해 500(k6 'other')으로 샌다. v3에선 타임아웃 미발생으로 ⓐ/ⓑ가 음성(503=0)이었지만, 분류 코드 자체의 실주행 증거는 v4/v5의 ⓒ에서 확보했다.
3. **출처**: analysis.md v4/v5 §결과(ⓒ 249,563·281,977, 미분류 0) + v3 음성 결과 절; 코드 `CouponDbExceptionClassifier.java`(ⓐ/ⓑ), `LockNotAcquiredException.java`(ⓒ).
4. **면접 방어**: "v3는 503=0인데 분류가 동작하는 건 어떻게 아나?" → Y. 분류 코드 실주행은 v4/v5 ⓒ로, v3는 '음성 결과(빈칸 아님)'로 문서가 구분.
5. **정직성 플래그**: 없음. (v3 ⓐ/ⓑ는 '음성=발견'으로 표기, '검증 실패'로 오독 금지.)

### E-4. v3 음성 결과를 적극 기록 — 경합 흡수 = DB 큐 증거
1. **이력서용**: v3에서 풀이 포화(HikariPool active 10/10, pending 189)됐는데도 503=0인 **음성 결과를 빈칸이 아닌 발견으로 기록해, "DB 행 락이 connection-timeout 30s 안에서 경합을 거절이 아니라 지연(성공 p95 2.6s)으로 흡수한다"는 증거로 활용**.
