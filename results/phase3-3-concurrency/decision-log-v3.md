## 0. 구성

본문(§1~§5)은 매 전환점의 선택지를 **조건별로 중립 나열**한다 — 어느 게 일반적으로 낫다가
아니라, 어떤 조건이 어느 선택을 부르는가. 그 위에서 §6은 **이 워크로드·이 제약**이라는 좌표를
고정하고, 거기서 내가 내린 결정(v3)과 근거를 명시한다. 중립 비교가 재료, §6이 판단이다.

세 축으로 읽는다 — **정합 범위**(어디까지 같은 결과를 보장하나) / **경합 흡수**(직렬화 비용을
어떻게 배출하나) / **갱신 정책**(보유 중 만료를 어떻게 다루나). 정합 판정은 공통으로
`coupon.issued` 카운터가 아닌 `SELECT COUNT(*) FROM coupon_issue`(= `actual`) 행 수로 한다.

## 1. 직렬화 수단 (v1→v2 자리) — 조건별 중립 정리

| 수단 | 맞는 조건 | 부적합 조건 |
|------|-----------|-------------|
| 무락 | 경합 거의 없음 / 초과 허용 집계 | 한정 수량 + 동시 요청 |
| 낙관적 락 (`@Version`) | 저경합 — 충돌 드묾 | 고경합 단일 핫키 — 재시도 폭풍 |
| `ReentrantLock` | 타임아웃·공정성 등 세밀 제어 필요 | 단일 임계 구간 — 복잡도만 |
| `synchronized` | 단일 JVM + 단순성 우선 | 다중 프로세스 정합 필요 |

- **무락(v1)**: 한정 수량(`total=100`) 워크로드엔 부적합. 실측 `actual=999`(+899, 10배 초과).
  부수 교훈 — 카운터 `coupon.issued`는 100으로 캡돼 "한도 지켜진 듯" 보이나(lost update), 진실은
  행 수 999. 무락 조건이라도 정합 판정은 행 수로.
- **`synchronized`(v2)**: 단일 JVM·단순성 조건의 도구. `CouponIssueServiceV2`는 프록시 함정
  (`@Transactional`+`synchronized` 동시 → 커밋이 모니터 밖 → 단일 JVM서도 초과)을 피하려고
  모니터를 tx 경계 바깥(파사드)에 두고 실제 tx는 별도 빈 `CouponIssueServiceV2Inner` 프록시
  호출(락 ⊃ tx). 실측 `actual=100` **PASS**, 카운터까지 진실과 일치.
- **경계**: `synchronized`의 정합 범위는 그 JVM 프로세스 안까지. 다중 인스턴스면 각자 별도
  모니터라 깨짐(단일 JVM 측정으론 미실증 — **알려진 한계**).

## 2. 공유 직렬화 좌표 (v2→v3 자리) — 조건별 중립 정리

| 수단 | 맞는 조건 | 부적합 조건 |
|------|-----------|-------------|
| DB 유니크 제약 | "같은 키 중복" 차단 | "서로 다른 주체의 초과" — 유니크가 닿지 않음 |
| 낙관적 락 (`version`+재시도) | 공유 + 저경합 | 공유 + 고경합 핫키 — 재시도 폭풍 |
| 비관적 행 락 (`FOR UPDATE`) | 공유 + 고경합 + 보호대상 DB내 | 보호대상 DB밖 / 풀 점유가 치명적 |

- **비관적 행 락(v3)**: `CouponIssueServiceV3`은 v2와 정반대 — 행 락은 커밋 시 풀리므로 락
  획득·검사·발급을 **하나의 `@Transactional`** 안에서(단일 빈, 파사드 없음).
  `findByIdForUpdate`로 행 락 후 검사/발급. 실측 `actual=100` **PASS**.
- **딸려오는 특성 — 풀 압박**: FOR UPDATE가 커넥션 쥔 채 행 락 대기 → 대기 요청이 커넥션 점유.
  실측 HikariPool active=10/10(포화), pending=189, idle=0. 결함이 아니라 선택의 특성(풀·타임아웃
  핀으로 측정·튜닝).
- **이 핀·부하의 음성 결과**: ⓐ(풀)/ⓑ(행락) 503 분류는 배선·풀 포화까지 검증됐으나 타임아웃
  미발생으로 503=0. 임계 구간이 짧아(수 ms) 커넥션 빠르게 순환 → connTO 30s·행락 50s 어느 쪽도
  미초과. 해석: **이 조건에선 DB 행 락이 경합을 거절(503) 아닌 지연(성공 p95 2.6s)으로 흡수.**

## 3. 분산 락 (v3→v4 자리) — 조건별 중립 정리

분기점은 **"보호 대상이 어디 있나"**.

| 축 | DB 행 락 (v3) | Redis 분산 락 (v4/v5) |
|----|---------------|----------------------|
| 보호대상 DB 안 | 락↔데이터 동일 시스템(원자적) | 락↔데이터 분리(fencing 공백) |
| 보호대상 DB 밖(외부 API 등) | 닿지 않음 | **적합** |
| DB 부하 분리 | 락 경합이 DB·풀에 실림 | DB 밖으로 분리 |
| 인프라 비용 | 추가 0 | Redis SPOF·운영 |
| 다중 인스턴스 정합 | 공유 DB 행으로 이미 확보 | 공유 Redis로 확보(v3 대비 *범위* 추가 아님) |

두 분산 구현(둘 다 fail-fast):

- **v4 — Redisson `RLock`**: 파사드(락 ⊃ tx), `tryLock(0,…)` fail-fast, leaseTime 미지정 →
  **워치독 자동 갱신**. 가드(미획득 unlock 금지 / RedisException 단일 ⓒ). 실측 정합 `≤ total`;
  10s `actual=62`(대기 큐 없는 fail-fast 정상 미충전), 90s `actual=100` 수렴. 503 ⓒ 249,563
  (미분류 0), 거절률 99.9%.
- **v5 — 커스텀 `SET NX`+Lua**: v4 동형 파사드, **고정 TTL 30s 무갱신**. 락 전용
  `StringRedisTemplate`로 직렬화 함정(JSON 따옴표→Lua 비교 실패→release 불가) 회피. 실측
  `actual=100` **PASS**, 503 ⓒ 281,977(미분류 0), 거절률 99.7%.

> 거절률 99%대는 **단일 핫키 + 즉시실패**의 귀결이지 분산 락 일반의 성질이 아니다(범위 한정).

## 4. 갱신 정책 (v4 vs v5) — 조건별 중립 정리

| 정책 | 맞는 조건 | 실패 모드 |
|------|-----------|-----------|
| 워치독 자동 갱신 (v4) | hold 가변·예측 불가 | 클라이언트 갱신 복잡도 |
| 고정 TTL 무갱신 (v5) | hold 짧고 TTL≫worst-case | TTL 조기 만료 → 만료-중간탈취 |

**정상 부하로는 둘을 가를 수 없다(발견8)**: hold(수 ms) ≪ TTL(30s)이라 고정 TTL이 임계 구간
중간 만료될 일이 없음 → 워치독이 막을 사건 부재. v5(28.4/s, p95 106ms) > v4(6.3/s, p95 418ms)
차이는 갱신 정책이 아니라 **대기/락 구현 아티팩트**(Redisson pub/sub+워치독 vs 커스텀 경량
SET NX). 어느 쪽이 빠르다는 인과를 **세우지 않는다.** 진짜 차이는 hold>TTL 스톨 조건에서만(§5).

## 5. fencing (스톨 데모) — 분산 락 공통의 경계

`CouponStallDemoService`, 통제 `total_qty=1` · **`ttl=1s < stall=3s`**. 스톨 중 보유 TTL 만료 →
다른 홀더가 만료된 락 훔쳐 동시 발급.

- **결과**: A `released=false`(compare-del 오해제 차단 ✓)인데도 **`actual=2 > total=1`**
  (user 9001·9002 둘 다) = **동시 점유 ✗**.

**중립 사실**: 안전한 release(오해제 차단) ≠ 상호배제(동시 점유 차단). compare-del은 전자만,
후자는 **fencing token 없이는 어느 분산 락도 못 줌**(워치독도 GC pause/네트워크 단절엔 동일).
즉 갱신 정책과 무관하게 Redis 분산 락은 fencing-safe하지 않다(이 초과는 데모 통제 산물 — 정상
v4/v5는 초과 0). 반면 락↔데이터가 같은 트랜잭션인 v3는 만료-중간탈취 자체가 불가 → 이 공백이
구조적으로 없다. 우열이 아니라 **메커니즘 차이**(락을 데이터에서 떼었나).

## 6. ★ 이 워크로드·이 제약에서 내가 내린 결정 — v3 (명시)

여기서부터는 중립 나열이 아니라 **단정**이다. 좌표를 고정한다: **단일 스키마 모놀리식 +
단일 핫키(couponId=1) 고경합 + 임계 구간이 곧 DB 쓰기**(`coupon` UPDATE + `coupon_issue` INSERT).
이 좌표에서 정규 발급 경로(`POST /api/coupons/issue` 무버전)를 **v3 (DB 비관적 행 락)에 배선했다.**
v1·v2·v4·v5는 비교용으로 공존하되 운영 트래픽과 무관하다.

**근거 X — 락↔데이터 동치(원자성). 이게 결정의 핵심이다.**
이 워크로드의 보호 대상(coupon 행)이 **이미 DB 안**에 있다. v3는 락(FOR UPDATE 행 락)과 데이터가
**같은 DB·같은 트랜잭션** 안에 있어 원자적이다 — 락은 커밋 시 풀리므로 만료-중간탈취 자체가
**불가**, **fencing 공백이 구조적으로 없다.** 락을 Redis로 빼는 순간 락↔데이터가 다른 시스템으로
분리되고 그 공백이 열린다. **§5 스톨 데모 `actual=2`가 그 공백의 실측 증거다.** 그래서 v3는
v4/v5보다 단지 "충분"한 게 아니라 **이 워크로드에선 더 안전하다.**

**근거 보강:**
- **다중 인스턴스 정합도 이미 v3가 준다**: 공유 DB 행 락이라 인스턴스를 늘려도 모두 같은 행 락
  경유 → 경계 초월. **Redis는 스케일아웃의 전제가 아니다.** (단일 JVM 측정으론 미실증한 개념적
  보장 — **알려진 한계, 다음 후보**. v4/v5가 v3 넘어 더해주는 건 정합의 *범위*가 아니라 비-DB
  임계 구간 보호뿐.)
- **대가는 수용 가능**: v3 풀 압박(active 10/10, pending 189)은 측정·튜닝 가능한 비용이며 본
  워크로드 규모에서 감당된다.
- **throughput은 근거로 쓰지 않았다**: v3(317.5/s) > v2(263.6/s)·v5 > v4 같은 반전은
  **관측·미증명·단일 런**이다. 경합을 통일하면 어떻게 수렴하는지는 별도 통제 실험에서 확인했고
  (원본 사다리에선 직접 비교하지 않으며 수치도 끌어오지 않는다), 결정 근거는 throughput이 아니라
  위의 **구조적 안전(fencing 무공백)**이다.

**이 결정의 범위와 반대 조건 (단정이되 무조건은 아님):**
이 선택은 **인프라 맥락의 함수**다. 맥락이 바뀌면 — Redis가 이미 핵심 캐시로 깔려 있고 + DB
부하 분리가 절실하며 + 보호 대상이 **DB 밖**(외부 API 호출 멱등성, 비-DB 자원)이라면 — v4로
이전한다. 즉 **Redis 분산 락이 맞는 자리는 보호 대상이 DB 밖일 때**이고, 그땐 락을 데이터에서
떼어낼 수밖에 없으니 분산 락이 본래 자리를 찾는다. 하지만 DB 행 보호엔 락을 데이터에서 떼어내는
것 자체가 역효과(fencing 공백 + SPOF)다.

**결론**: "왜 분산 락(트렌드)을 안 썼나"의 답은 트렌드 무지가 아니라 **워크로드 적합성 판단**이다.
사다리를 커스텀 분산 락까지 끝까지 구현해 보고도, 이 좌표의 정답은 DB 행 락(v3)이라고 단정한다.
