## 2. 예보 밖 사고 — 검증 설계가 잡은 것 (은폐 없음)

지도가 예측하지 못한 측정 사고 2건. 둘 다 *은폐할 결함*이 아니라 검증 설계(loud-fail)가 일했다는 증거다.

1. **redis 격리 누수(설정 버그)** — 전용 격리 스택의 redis가 대체 포트인데, 앱의 `StringRedisTemplate`이
   `RedisConfig`의 무인자 `LettuceConnectionFactory`(localhost:6379 하드코딩) 탓에 상태 해시를 본체 redis로
   기록했다(Redisson은 정상). 앱이 redis 클라이언트를 둘 가졌고 그중 하나만 격리됐던 것. **터미널 회계
   loud-fail**(terminal=0 ≠ 202)이 즉시 FAIL로 검출 → 설정 수정(`spring.data.redis` 준수) + 본체 복원 + 재측정.
2. **stale app 포트 충돌** — 버전 전환 시 직전 앱이 8080을 점유해 새 앱 바인드 실패 → stale 앱이 404 응답.
   k6 회계(202=0)가 FAIL로 검출 → 앱 정리 후 재측정.

→ 둘 다 정적 검수가 아니라 **하네스의 측정 레벨 loud-fail**이 잡았다. 무효 런은 삭제하지 않고
[`INVALID-RUNS.md`](../../results/phase3-4-async/INVALID-RUNS.md)에 콘솔 증거로 보존했다. 교훈: 격리 검증은
앱의 *모든* 외부 연결(redis 클라이언트가 복수일 수 있음)을 전수 확인해야 한다.

## 3. v3 프레임 고정 (계승 확인)

이 실험은 phase 3-3의 v3 채택을 흔들지 않는다 — v3 대체 탐색이 아니라 *같은 게이트(초과발급 0)를 통과하는
다른 구조(큐)의 비용 프로파일 측정*이다. 전 버전 초과발급 0, E2E 발급 지연은 v3 동결본과 부하 프로필이
달라 직접 비교 금지(참조만). 서사는 3축(생존·유실·중복) — 상세는 [회고 리포트](phase3-4-async-issuance.md).
