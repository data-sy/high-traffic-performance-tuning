Part 0 · Prerequisites

본문에 들어가기 전, 여덟 가지만 챙기자

phase 3-3의 일곱 카드가 "락"을 위한 장비였다면, 이번 여덟 카드는 "큐"를 위한 장비다. 이미 아는 카드는 건너뛰어도 된다 — 각 카드 하단에 어느 장면에서 필요한지 적어 두었다.

P1

동기 → 비동기 — "응답"의 의미가 바뀐다

동기 발급에서 200 OK는 "발급이 끝났다"는 뜻이다. 비동기에서 응답은 202 Accepted — "접수했고, 결과는 나중에"가 된다. 발급 여부는 응답이 아니라 별도 경로(상태 조회·알림)로 전달된다. 시스템이 잠시 서로 다른 답을 하다가 결국 한 답으로 수렴하는 이 성질이 최종 일관성이다.

어디서: §1 전체, §4 T3·T7 — 이 의미 변화를 놓치면 측정도 UX도 무너진다.
P2

스레드풀 해부 — core, max, 그리고 줄 서는 순서

스레드풀에는 상시 인원(core), 최대 인원(max), 대기열(queue)이 있다. 직관과 다른 함정: Java 기본 정책은 core가 다 바쁘면 먼저 큐에 줄을 세우고, 큐가 가득 차야 max까지 증원한다. 즉 큐를 무제한으로 두면 max는 영원히 안 쓰인다. 큐도 차고 max도 차면 거부 정책이 발동한다.

어디서: §3 v6a, §4 T2 — 기본값을 모르면 OOM 아니면 무한 스레드.
P3

@Async도 프록시다 — v2의 데자뷰

phase 3-3에서 @Transactional이 프록시라서 v2의 락 위치가 갈렸던 것을 기억하는가. @Async도 정확히 같은 메커니즘이다 — 같은 클래스 안에서 자기 메서드를 직접 부르면 (self-invocation) 프록시를 건너뛰어 그냥 동기로 실행된다. 예외도 조용히 삼켜질 수 있다(반환형이 void면 호출자에게 전파 안 됨).

어디서: §4 T1 — 이번 phase에서 가장 먼저 밟을 가능성이 높은 함정.
P4

브로커, 프로듀서, 컨슈머 — 그리고 ack

큐가 프로세스 밖으로 나가면 역할이 셋으로 갈린다: 넣는 쪽(프로듀서), 보관하는 쪽(브로커), 꺼내 처리하는 쪽(컨슈머). 핵심은 "꺼냈다"와 "처리를 끝냈다"가 다른 사건이라는 것 — 처리 완료를 브로커에게 알리는 신호가 ack다. ack가 없는 큐에서 컨슈머가 꺼낸 직후 죽으면, 그 메시지는 세상에서 사라진다.

어디서: §3 v6b→v6c를 가르는 기준, §4 T5.
P5

전달 보장 — 정확히 한 번은 환상이다

메시지 전달 보장은 셋뿐이다. at-most-once(유실 가능), at-least-once(중복 가능), 그리고 exactly-once — 마지막 것은 브로커 구간에서는 흉내 낼 수 있어도 DB 커밋까지 포함한 끝단에서는 공짜로 주어지지 않는다. 실무의 답은 정해져 있다: at-least-once를 받아들이고, 처리를 멱등하게 만든다.

어디서: §3 v6c, §4 T6 — 멱등 키 설계의 근거.
P6

Redis 안의 세 후보 — Pub/Sub, List, Stream

이미 떠 있는 Redis 안에 큐 후보가 셋 있다. Pub/Sub은 구독자가 없는 순간의 메시지가 증발한다 — 발급 요청 저장소로는 탈락. List(LPUSH+BRPOP)는 진짜 큐지만 꺼내는 순간 큐에서 사라진다 — ack 없음. Stream은 컨슈머 그룹과 PEL, XACK을 갖춘 본격 큐다.

어디서: §3 사다리의 등반 코스 그 자체.
P7

백프레셔 — 들어오는 속도 > 나가는 속도라면

적재가 초당 500건인데 소비가 초당 100건이면, 큐 깊이는 초당 400씩 그냥 자란다. 큐는 폭주를 막아주지 않는다 — 폭주를 지연으로 바꿔서 뒤로 미룰 뿐이다. 무한 큐는 지연 폭탄이 되고, 유한 큐는 결국 입구에서 거절을 부활시킨다. 이 압력을 생산자 쪽으로 되미는 모든 장치를 백프레셔라 부른다.

어디서: §4 T7, §5 큐 깊이 지표. 아래 시뮬레이터로 직접 체감.
P8

측정 용어의 의미 변화 — p95가 거짓말을 시작한다

phase 3-3에서 응답시간은 곧 처리시간이었다. 비동기에서는 응답시간이 "접수에 걸린 시간"일 뿐이다. 그래서 새 지표가 필요하다: E2E 발급 지연(적재→커밋), 큐 깊이, 그리고 수렴 시간(마지막 발급 커밋까지). HTTP p95만 보면 시스템이 빨라진 것처럼 보인다.

어디서: §4 T3·T4, §5 전체 — 이번 phase 측정 규율의 심장.
비유 하나로 끝까지 간다. phase 3-3이 "점원과 장부"였다면 이번엔 은행 창구와 번호표다. 동기 발급(v3)은 창구 앞에 직접 줄을 서는 것 — 줄 서는 동안 내 몸(커넥션·스레드)이 자리를 차지한다. 비동기 발급은 번호표를 뽑고 자리를 비우는 것 — 입구 직원(프로듀서)은 번호표만 주고(202), 창구 직원(컨슈머)이 순서대로 처리하고, 결과는 전광판(상태 조회)에 뜬다. 번호표 기계가 종이(인메모리 큐)냐 중앙 서버(Redis)냐, 부른 번호를 "처리 완료" 도장(ack) 찍느냐가 이번 사다리의 칸이 된다.
Part 1 · The Starting Point

출발점 — 동결본을 다시 읽는다

phase 3-4는 새 문제에서 출발하지 않는다. phase 3-3이 끝났을 때 장부에 남아 있던, 해결됐지만 비용이 측정된 숫자에서 출발한다.

v3(DB 비관적 행 락)는 정합성 게이트를 통과했고, 워크로드 적합성을 근거로 프로덕션 경로에 채택됐다. 그 결정은 이번 phase에서도 흔들리지 않는다. 다만 동결본에는 v3가 그 정합성을 지키는 방식의 비용이 함께 적혀 있다:

이 숫자들을 한 문장으로 다시 읽으면 — 모든 요청이 결국 처리됐지만, 줄을 서는 동안 커넥션과 스레드를 쥔 채 서 있었다. 풀 10차선이 전부 잠기고 189명이 풀 앞에 줄을 섰다. 줄 자체는 죄가 없다. 문제는 줄이 비싼 자원을 점유한 채 늘어선다는 것이다.

지금 — 동기 발급 (v3)
요청→ 스레드 점유→ 커넥션 점유→ 행 락 대기→ 발급 커밋→ 200 "발급됨"
붉은 구간 전체가 "응답시간"이고, 그동안 스레드·커넥션이 잠긴다. 줄이 길수록 잠김도 길다.
가설 — 비동기 발급 (v6 시리즈) 예측 ●●●
요청→ 큐에 적재→ 202 "접수됨" ‖ 컨슈머→ 행 락·커밋→ 상태: 발급됨
응답 경로와 처리 경로가 분리된다. 스레드·커넥션 점유는 컨슈머 쪽으로 이동하고, 사용자 쪽 줄은 "번호표 대기"로 바뀐다. 줄이 사라지는 게 아니라 — 큐로 옮겨가는 것이다.
프레임 고정. phase 3-3의 결론 — 한정 수량 쿠폰에서 정합성은 협상 대상이 아니라 게이트고, 성능은 그 제약 안의 비용이다 — 는 이번에도 그대로다. 3-4는 "v3보다 빠른 것"을 찾는 실험이 아니라, 같은 게이트(초과발급 0)를 통과하는 또 다른 구조의 비용 프로파일을 측정하는 실험이다. 비교의 단위가 응답시간에서 E2E 지연으로 바뀐다는 점만 다르다.
Part 2 · The Fork

첫 갈림길 — 재고 판정을 어디서 할 것인가

코드를 쓰기 전에 만나는 가장 큰 설계 분기. 100장 한정인데 10만 명이 달려들면, "당신은 안 됩니다"를 입구에서 말할 것인가, 창구에서 말할 것인가.

Fork A — 입구 판정

적재 전에 Redis 원자 카운터로 선판정. 탈락자는 즉시 409, 큐에는 당첨 후보만 들어간다.
  • 탈락이 즉시 확정 — 사용자는 기다리지 않고 결과를 안다
  • 큐가 슬림하다 — 깊이 ≤ 수량, 백프레셔 걱정이 거의 없다
  • 진실 소스가 둘이 된다 — Redis 카운터 vs coupon_issue 행 수
  • 컨슈머가 발급에 실패하면 카운터를 되돌리는 보상이 필요하다
  • phase 3-3에서 세운 규율("진실 소스는 행 수 하나")과 긴장 관계

Fork B — 출구 판정

일단 전부 적재하고 202. 재고 판정은 컨슈머가 DB 앞에서 한다.
  • 진실 소스가 하나다 — 판정 지점이 DB뿐, 보상 로직 없음
  • 구조가 단순해서 사다리 첫 칸으로 적합
  • 큐에 초과 적재 — 999명 적재되면 899명이 나중에 실패 통보를 받는다
  • "202 받았는데 결국 탈락"이라는 UX — 상태 모델이 필수가 된다
  • 큐 깊이·소비 시간이 수요에 비례해 자란다

지금 단계의 결정: 결정하지 않는다. 사다리는 Fork B(단순한 쪽)로 시작하고, Fork A는 마지막 칸 또는 후속 보강으로 남긴다 — 입구 판정의 "이중 진실 소스" 문제는 그 자체로 측정할 가치가 있는 별도 주제이기 때문이다. 이 분기는 스펙 단계의 승인 게이트 항목으로 올린다. 예측 ●●○

번호표로 말하면. Fork A는 번호표 기계가 "오늘분 마감"을 미리 알고 101번째부터 표를 안 주는 것. Fork B는 일단 모두에게 표를 주고, 창구에서 "죄송합니다, 앞에서 마감됐네요"라고 말하는 것. A는 기계가 똑똑해야 하고(그리고 기계와 창구 장부가 어긋나면 안 되고), B는 헛걸음이 생긴다.
Part 3 · The Imagined Ladder

예상 사다리 — v6a → v6c, 큐가 점점 단단해진다

phase 3-3의 사다리가 "락의 정합 범위"를 한 칸씩 넓혔다면(JVM → DB → Redis), 이번 사다리는 큐의 생존 범위를 넓힌다. 칸마다 무엇이 살아남고 무엇이 사라지는지가 등반의 서사다. 아래 구현 스케치는 전부 예측 ●●○ — 본 실행에서 형태가 바뀔 수 있다.

i

큐의 생존 범위

큐가 어디에 사는가 — JVM 힙(앱이 죽으면 같이 죽음) → Redis(앱과 독립 생존).

ii

유실의 양상

앱 사망 시 통째 증발 → 꺼낸 직후 사망분만 유실 → PEL에 남아 재전달.

iii

중복의 등장

재전달이 생기는 순간 중복이 태어난다. 중복을 없애는 게 아니라 무해하게 만든다(멱등).

v6a큐 = JVM 힙예측 ●●●

@Async + 인메모리 스레드풀 — 일단 응답에서 처리를 떼어낸다

번호표 기계가 "메모장 한 장". 입구 직원이 요청을 메모해 두고 즉시 202, 뒷방 직원(풀 스레드)이 메모를 집어 처리한다.

가장 작은 한 걸음. 컨트롤러는 적재만 하고 202를 반환, ThreadPoolTaskExecutor가 처리를 맡는다. 이 칸의 목적은 성능이 아니라 의미 변화의 체감이다 — 성공 시그니처가 어떻게 깨지는지(§4 T3), 응답 p95가 어떻게 거짓말을 시작하는지(§4 T4)를 가장 싼 비용으로 관찰한다.

// 스케치 — 빈 분리로 self-invocation 회피 (P3, v2의 교훈 재사용)
@Service // 파사드: 적재만
public class CouponIssueFacade {
    public IssueTicket enqueue(Long couponId, Long userId) {
        worker.processAsync(couponId, userId); // 다른 빈 → 프록시 경유 보장
        return IssueTicket.accepted(...);      // 202
    }
}
@Service // 워커: 처리만
public class CouponIssueWorker {
    @Async("couponExecutor") // 기본 executor 금지 — §4 T2
    public void processAsync(Long couponId, Long userId) { // 내부에서 v3 경로 호출 }
}
이 칸이 못 하는 것: 앱이 재시작하면 큐(스레드풀 대기열)가 통째로 증발한다. 202를 받은 사용자의 요청이 흔적 없이 사라진다 — at-most-once보다도 약하다. 다중 인스턴스에서는 큐가 인스턴스 수만큼 쪼개진다.
v6b큐 = Redis List예측 ●●○

LPUSH + BRPOP 워커 — 큐가 앱 밖으로 나간다

번호표 기계가 "중앙 서버"가 된다. 입구가 죽어도 이미 뽑힌 번호표는 살아 있다.

프로듀서는 LPUSH, 별도 워커 루프가 BRPOP으로 꺼내 처리한다. 앱 재시작에도 큐가 생존하고, 워커를 다른 프로세스로 떼어낼 수 있다 — phase 3-3 백로그였던 다중 인스턴스 실증의 자연스러운 입구가 여기서 열린다.

이 칸이 못 하는 것: BRPOP은 꺼내는 순간 큐에서 지운다. ack가 없다. 꺼낸 직후 ~ 커밋 전 사이에 워커가 죽으면 그 한 건은 유실된다(at-most-once 구간이 남음). "유실되는 순간"을 의도적으로 재현해 기록하는 것이 이 칸의 핵심 실험이다.
v6c큐 = Redis Stream예측 ●●○

Stream + 컨슈머 그룹 — ack와 재전달, 그리고 중복의 탄생

부른 번호를 "처리 완료" 도장(XACK)으로 마감한다. 도장 없이 사라진 번호는 다른 창구가 회수한다.

XADD로 적재, 컨슈머 그룹이 XREADGROUP으로 분배받아 처리 후 XACK. 컨슈머가 죽으면 메시지는 PEL에 남고, XAUTOCLAIM으로 다른 컨슈머가 회수한다 — 드디어 at-least-once. 그리고 그 대가로 중복이 태어난다: 처리는 끝났는데 XACK 직전에 죽으면, 같은 요청이 다시 배달된다.

-- 중복을 무해하게: DB가 멱등의 최후 방어선 (P5)
ALTER TABLE coupon_issue
  ADD CONSTRAINT uq_coupon_user UNIQUE (coupon_id, user_id);
-- 재전달분은 INSERT 충돌 → "이미 발급됨"으로 흡수. 행 수는 절대 늘지 않는다.
이 칸이 못 하는 것: exactly-once는 여기서도 없다. 우리가 만든 것은 "유실 없음 + 중복은 DB 유니크 제약이 흡수"라는 조합이지, 마법이 아니다. 멱등 키가 없는 부수효과(알림 발송 등)는 여전히 중복될 수 있다 — 범위 밖으로 명시한다.
칸큐의 생존앱/워커 사망 시중복멱등 키다중 인스턴스
v6a @AsyncJVM 힙대기분 전체 증발없음불필요큐 분열
v6b ListRedis꺼낸 1건 유실 가능없음권장가능(경쟁 BRPOP)
v6c StreamRedisPEL 재전달가능필수(유니크)컨슈머 그룹

Kafka는 이 표의 오른쪽 끝에 자연스럽게 이어지는 칸이지만(파티션·오프셋·리밸런싱), 브로커 인프라가 새로 추가되는 비용이 커서 이번 phase 범위 밖 — 백로그로 명시한다. v6c까지가 "이미 떠 있는 Redis로 어디까지 가는가"의 끝이다.

Appendix

용어 정리

202 Accepted
요청을 접수했고 처리는 나중에 한다는 HTTP 상태코드. 성공도 실패도 아직 보장하지 않는다 — 결과는 별도 경로로.
최종 일관성 (eventual consistency)
갱신 직후엔 보는 위치마다 값이 다를 수 있지만, 새 갱신이 없으면 결국 한 값으로 수렴하는 일관성 모델.
프로듀서 / 브로커 / 컨슈머
메시지를 넣는 쪽 / 보관·분배하는 쪽 / 꺼내 처리하는 쪽. 큐가 프로세스 밖으로 나가면 역할이 이렇게 갈린다.
ack
"처리 끝났음"을 브로커에 알리는 확인 신호. "꺼냈다"와 "끝냈다"를 분리하는 장치.
at-most-once / at-least-once
최대 한 번(유실 가능, 중복 없음) / 최소 한 번(유실 없음, 중복 가능). 실무 기본값은 후자 + 멱등 처리.
멱등성 (idempotency)
같은 요청을 여러 번 수행해도 한 번 한 것과 결과가 같은 성질. 중복 전달을 무해하게 만든다.
컨슈머 그룹 / PEL / XACK / XAUTOCLAIM
Redis Stream의 분배 단위 / 배정됐지만 미완료인 메시지 목록 / 완료 도장 / 죽은 컨슈머의 미완료분 회수 명령.
백프레셔 (backpressure)
소비 속도를 넘는 유입을 생산자 쪽으로 되밀어 감속·거절시키는 흐름 제어.
큐 깊이 / E2E 발급 지연 / 수렴 시간
쌓여 있는 미처리 건수 / 적재→커밋 전 구간 지연 / 마지막 발급 커밋까지 걸린 시간. 비동기 측정의 3대 신규 지표.
graceful shutdown
종료 신호를 받으면 새 일은 안 받고 진행 중인 일은 끝내고 내려가는 종료 방식.
self-invocation
빈 내부에서 this로 자기 메서드를 호출하는 것. 프록시를 건너뛰어 @Async·@Transactional이 무력화된다.
DLQ (dead letter queue)
반복 실패한 메시지를 격리 보관하는 별도 큐. 이번 범위 밖이지만 v6c 다음 칸의 단골 손님.
