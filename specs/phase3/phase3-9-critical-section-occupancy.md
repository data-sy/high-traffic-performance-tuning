# Phase 3-9 — 직렬 임계 구간: in-lock 왕복을 줄이고, 그 단축이 throughput으로 번역되는지 *반증 가능하게* 측정한다

> **정방향(to-build) 스펙.** phase 3-3(동시성 — 쿠폰 발급 락 사다리, v3=SELECT FOR UPDATE 채택·완료)의 **지연(latency)
> 후속**이다. 3-3이 *어느 락이 정합을 지키나*를 닫았다면, 3-9는 그 v3가 남긴 지연(p95 2630ms·pending 189)의 원천 —
> 직렬 임계 구간의 in-lock DB 왕복 — 을 한 칸씩 줄이고, 그 단축이 사용자 체감(throughput)으로 번역되는지를 *반증
> 가능하게* 측정한다. **채택 결정이 아니다**(3-7·4-1 규율 계승): "무엇을 줄이면 무엇이 commit floor에 가려지는가"를
> 측정으로 가른다. ROADMAP Stage 3 단일 노드 성능 계열.

## 실행 개시 — 이 스펙을 받은 빌드 세션에게

> 이 스펙 하나가 R0~R4 구현·측정의 **단일 진실 소스**다. 아래 순서대로 진행하되 각 관문에서 멈춰 보고할 것.
> 이 세션은 **콜드 세션**이어야 한다 — 이 스펙 밖의 과거 대화 맥락을 끌어오지 말 것(맥락 과투입이 과거에 실측을 뒤집은 적 있음).

**Step 0 — 안전 확인 (진행 전 필수).**
- 워킹트리·`results/`에 phase 3-9를 동시 작업 중인 다른 세션/프로세스가 없는지 확인. 있으면 멈추고 보고.
- 다른 작업(다른 프로파일 앱·다른 프로젝트 세션)을 깨지 않는다.

**Step 1 — 측정 기판 확보 (엔지니어링 요구사항).**
- **base 프로파일**(utf8mb4 · redis 6379 · 캐시 빈 없음)로만 측정한다. **`phase3-8` 프로파일 금지** — `SET NAMES latin1`이
  dirty-flush `UPDATE coupon`의 `name`을 누적 truncation(1406)시켜 v3가 500으로 샌다(Context 참조).
- 클린 base 프로파일 앱을 확보한다. **직전 파일럿이 이미 클린 base 앱을 띄워뒀다면 재사용**(예: 8080).
- coupon 로우는 매 런 전 **canonical seed(`total_qty=100` · `issued=0` · `coupon_issue` 비움)**로 리셋.

**Step 2 — 구현·측정 (칸당 한 세트 · 3-3 "구현→측정→기록" 규율).**
- **R0부터**(현행 v3 *충실 복제* — literal 재사용 아님). 이어 R1(진단·풀 스윕, 부하 측정 중 가장 먼저) → R2 → R3 → R4.
  **R5는 분석 전용·격리 빌드**(단일 빌드 혼합 금지).
- 각 칸: ① **단일요청 프로브(동시성 0)로 in-lock 왕복 수 확정**(표와 대조 — R0=4·R1=4·R2=4·R3=3·R4=2) →
  ② 성능축 부하 측정 → ③ `results/`에 기록.
- **반드시 배선할 3개 게이트**(미배선 시 측정 무효): (i) 칸별 프로브 카운트, (ii) **전 칸(R0~R4) flush 순서 게이트**
  (특히 R2 `existsBy` 앞 managed 접근 금지), (iii) **`PreRegisteredAdjudicationGate`**(채점 스텝 게이트 — 부팅 빈 아님, M2).

**Step 3 — ε 재확정 (R4 빌드 후 필수).**
- 파일럿 `ε_hi=21.9%`는 **R0 단독 잠정치**다. R4 빌드 후 **R0·R4 각 ≥3런의 결합 CV `√(CV_R0²+CV_R4²)`의 신뢰구간 상한
  `ε_hi`**로 재산출·재동결(§측정축 규칙 1·M3).
- `ε_hi < 0.5` 확인돼야 사전 등록 판정 유효. **`ε_hi ≥ 0.5`면 판정 보류** — 헤드라인을 구조 카운트 + R3 3점 정성으로
  정직 후퇴하고 "부하로 못 가름"을 결론으로 기록(§측정축 규칙 2).

**산출물·커밋.**
- 결과는 `results/phase3-9-critical-section-occupancy/`에 적재(기존 phase3-3 결과 덮어쓰기 금지). 프로브 카운트·칸별
  throughput·비 `r`·판정 결과 기록.
- 커밋은 Conventional Commits(영문 제목 + 한글 본문). **push 금지 — 사람 게이트.**

**멈추고 보고할 지점:** git push 전 · R4에서 `ε_hi ≥ 0.5`일 때 · 프로브 카운트가 표와 불일치할 때 ·
코드 동일 칸(R0/R2/R3/R4)에서 `503>0`일 때.

## 정직한 헤드라인 (이 스펙이 *반증 가능하게* 입증하려는 것)

> **단일 핫 로우 비관락 워크로드에서, 직렬 임계 구간의 비용은 in-lock DB 왕복 *수*가 아니라 commit floor(X-락을
> COMMIT까지 쥐는, 못 줄이는 insert-flush/fsync)가 지배한다.** 따라서 왕복을 4→3→2로 깎는 것은 *구조적으로 실재*
> (코드/프로브로 카운트)하지만 throughput으로는 *거의 번역되지 않는다*(부하 런으로 반증 가능하게 측정). —
> 만약 throughput이 카운트 감소에 비례해 오르면(R4≈2×R0) 이 헤드라인은 **틀린 것**이고, 그 결과도 기록한다.

## Context (코드·동결 수치로 확인)

- **출발점 = 현행 v3**(`service/coupon/CouponIssueServiceV3.java`, PESSIMISTIC_WRITE): `findByIdForUpdate`(FOR UPDATE
  SELECT) → `existsByCouponIdAndUserId`(SELECT) → `coupon.issue()`(managed 엔티티 dirty) → `save`(INSERT) → **커밋 시
  Hibernate dirty-flush `UPDATE coupon`** → 커밋. **임계 구간 = 트랜잭션 전체**(락은 커밋 시 해제).
  - **임계 구간 in-lock DB 왕복 = 4문**(FOR UPDATE SELECT · existsBy SELECT · INSERT coupon_issue · UPDATE coupon).
    `findByIdForUpdate`가 `Coupon`을 managed 엔티티로 적재하고 `coupon.issue()`가 `issued`를 증가시키므로, 커밋 flush에서
    `UPDATE coupon SET issued=… WHERE id=?` 1문이 **락 보유 중** 추가 발화한다(`analysis.md`의 counter==actual==100이
    이 UPDATE 발화를 확증).
- **v3 동결 수치**(정본 = `results/phase3-3-concurrency/analysis.md`, 두 축 분리): 성능축 throughput 317.5/s ·
  p95 2630.2ms · 503=0 · Hikari active 10/10 · pending 189 / 정확성축 actual==counter==total==100 · 초과 0 PASS.
  **두 수치는 한 런이 아니다**(total=100이면 즉시 매진 throughput≈0, 대용량이면 행수≠100).
- **노이즈밴드 ε_hi 동결(측정 유효성 전제):** 사전 등록 판정(아래)이 성립하려면 v3 성공 throughput의 런-간 노이즈밴드가
  반증 문턱과 겹치지 않아야 한다. base 프로파일(utf8mb4·redis6379)에서 5×500VU 성능축(매 런 리셋)으로 사전추정:
  런 [229.0 · 257.2 · 244.1 · 252.2 · 292.6]/s → mean 255.0/s · CV_point **9.24%** · **`ε_hi`(95% 단측 상한, χ² σ-bound,
  n=5·α=0.05) = 21.9% < 0.5**. 따라서 밴드 비겹침(`1+ε_hi = 1.219 < 1.5`) 성립 → **throughput 채점 사전 유효**(명목화
  아님). 이 파일럿 ε_hi는 R0 단독이라 진짜 결합 `√(CV_R0²+CV_R4²)`는 다소 크나, ~√2×도 <0.5라 결론은 견고 —
  R4 빌드 후 결합 CV로 재확정한다.
  - **측정 기판 주의:** 캐시 측정용 `phase3-8` 프로파일은 `connection-init-sql: "SET NAMES latin1"`(이중인코딩 category
    우회)이 dirty-flush `UPDATE coupon`의 `name` 컬럼을 latin1 라운드트립으로 누적 재인코딩→길이 초과(1406 Data
    truncation)시켜 지속 부하에서 v3가 500으로 샌다. **본 측정은 base 프로파일 필수**(phase3-8 미적용).
- **스키마 불변**(`ddl-auto: validate`): R0~R4는 기존 `coupon.issued`/`total_qty`·`coupon_issue` UNIQUE 재사용으로
  스키마 변경 0. R5(@Version)만 컬럼 추가 → 충돌 + 의미론 비대칭(아래 R5).
- **에러 계약**(코드 확인): `CouponExceptionHandler` = `@RestControllerAdvice(basePackages="com.project.api.coupon")`
  **패키지 한정**. 503 ⓐ(POOL_TIMEOUT)/ⓑ(LOCK_WAIT_TIMEOUT)는 `CouponDbExceptionClassifier.classify`(1205만 매핑,
  1062 미매핑)가 만들고 **`CouponController.issueViaV3`의 try/catch 안에서만** 호출됨.
- **`innodb_lock_wait_timeout`**: compose 명시 없이 MySQL **기본 50s 의존**(R1 풀 스윕 전제).

## Goal

같은 정합(초과 0)·같은 정책(park·503=0)을 고정한 채, 쿠폰 발급 임계 구간의 **in-lock DB 왕복 수를 한 칸씩 바꾸고**,
(a) 그 수가 줄었음을 **단일요청 프로브로 정적·결정론 입증**하고, (b) 그 구조적 단축이 **throughput으로 번역되는지를
사전 등록한 문턱으로 *반증 가능하게* 판정**한다. **채택 결정이 아니다** — "무엇을 줄이면 무엇이 commit floor에
가려지는가"를 측정으로 가른다.

| 축 | 지표 | 읽는 법 |
|---|---|---|
| **구조 (정적·결정론)** | **요청당 in-lock DB 왕복 수** | **동시성 0 단일요청 프로브** 1회 + 코드 정적 카운트로 확정(부하 불필요·인터리브 없음). R0=4·R1=4·R2=4·R3=3·R4=2. *부하 실험의 산물이 아니라 코드 사실* — "입증"이 아니라 "확정"으로 다룬다. |
| **채점 (반증 가능)** | **R0↔R4 정량 throughput 비**(+ R3 정성 추세점) | 아래 §사전 등록 판정. R4가 유일 정량점·정본, R3는 정성 보강만(규칙 5). 부하 런이 H_floor를 **반증할 수 있다**. |
| **진단 (반증 가능)** | **R1 풀 스윕 throughput 기울기** | 풀↑에 throughput이 *평평*하면 천장=점유시간(H_floor 측), *오르면* 천장=풀 → 전제 반증. |
| 게이트 | 초과 0 / 행수==100 | 성능축=초과 0, 정확성축=행수==100. 깨지면 그 칸 무효. |
| 보조 | p95/p99 | R0 2630ms 대비. |
| 강등 | Hikari pending | 포화 폐루프에서 ≈tomcat_threads−pool, t·왕복수 불변. 성공 시그니처 아님. R1에서만 200−pool 관측. |

### ★ 사전 등록 판정 — 부하 런이 헤드라인을 깰 수 있게

두 경쟁 가설을 *런 전에* 등록하고, 관측이 어느 쪽인지 **숫자 규칙으로** 가른다.

- **H_floor (헤드라인):** 요청당 직렬시간 ≈ `commit_floor + k·(왕복수)`, 단 `commit_floor ≫ k·왕복`. → 예측:
  `r = throughput(R4)/throughput(R0) ≈ 1`(측정 노이즈 안). 왕복 2개를 깎아도 직렬시간의 작은 분율만 제거.
- **H_왕복 (반증 후보):** 요청당 직렬시간 ≈ `k·(왕복수)`, commit_floor 무시 가능. → 예측: `r ≈ count(R0)/count(R4)
  = 4/2 = 2.0`. throughput이 왕복 수에 반비례.

**판정 규칙(문턱은 *측정*에서 도출 — 단정 금지):**
1. **노이즈밴드 ε 측정:** R0·R4를 각 ≥3회 반복 → 비 `r=tput(R4)/tput(R0)`의 **결합 변동계수 `ε ≈ √(CV_R0² + CV_R4²)`**
   로 ±ε 산출(가정 아님, 실측 — R0 단독 CV는 R4 단일잡음을 흘려 ε 과소추정이라 금지). M2 핀·M3·`PreRegisteredAdjudicationGate`와
   동일 정의.
   **보수적 ε 입력·비대칭 차단:** 게이트가 쓰는 값은 ε *점추정*이 아니라 **결합 CV의 신뢰구간 상한 `ε_hi`**(소표본
   보수화)다. n이 작으면(≥3은 *하한*) CV 추정 자체가 표본오차로 흔들려 참 ε≥0.5인데 점추정이 <0.5로 나와 겹친 밴드가
   *조용히* 통과하는 비대칭(과대추정만 (i) 재측정을 트리거, 과소추정은 무트리거)이 생긴다 → **게이트는 `ε_hi`로 판정**해
   과소추정 통과를 구조적으로 막고, n은 파일럿 분산 기반으로 `ε_hi`의 CI가 충분히 좁아질 때까지 상향한다(반복 횟수 도출은
   §열린 결정). 이로써 '소표본 표본오차 → ε 과소추정 → 밴드 겹침 조용한 통과' 경로가 닫힌다.
2. **밴드 비겹침 선검사 — *판정 자격 게이트*:** 지지밴드 상한 `1+ε`가 반증 문턱 `1.5`보다 *작을* 때만(즉
   **`ε < (ρ*−1)/2 = 0.5`**) 세 밴드(지지/미결/반증)가 겹치지 않아 판정이 성립한다. 실측 ε가 `≥0.5`면 `1+ε ≥ 1.5`라
   지지밴드 `[1−ε, 1+ε]`와 반증밴드 `[1.5, ∞)`가 겹쳐 *같은* r이 '지지'이자 '반증'이 되는 동어반복이 생긴다. 따라서:
   **ε≥0.5면 (i) R0·R4 반복을 늘려 ε(결합 CV) 재측정 → (ii) 그래도 ε≥0.5면 이 부하 런은 헤드라인을 가를 해상도가
   없음(노이즈 > 신호)으로 *판정 보류*, 헤드라인을 입증/반증 어느 쪽으로도 단언하지 않는다.**(문턱 1.5를 ε에 맞춰 키우면
   H_왕복 신호 영역을 잠식해 무의미 → 문턱이 아니라 ε를 줄이거나 판정을 포기한다.)
   **이하 본 스펙의 모든 평문 ε 임계 비교(`ε<0.5`·`ε<0.165`·`ε≥0.5`)는 게이트 집행 시 점추정이 아니라 보수적 상한
   `ε_hi`(규칙 1)로 읽는다** — 평문 ε는 개념(노이즈밴드) 서술, 집행 기준은 항상 `ε_hi`.
3. **구조적 기준비:** `ρ* = count(R0)/count(R4) = 2.0`, 중간 칸 `ρ_R3 = count(R0)/count(R3) = 4/3 ≈ 1.33`.
4. **관측 r 분류(2의 밴드 비겹침 통과 후에만):**
   - `1 − ε ≤ r ≤ 1 + ε` → **H_floor 지지**(commit floor 지배, 헤드라인 **입증**). 구조적 단축이 번역 안 됨이 *측정으로* 확인.
   - `r ≥ 1 + (ρ*−1)/2 = 1.5` → **H_floor 반증·H_왕복 지지**(왕복 수가 천장을 구속, 헤드라인 **틀림**). 그대로 기록.
   - `1+ε < r < 1.5` → **미결**(commit floor 부분 지배). 헤드라인 단언 금지, 혼합으로 보고.
   - `r < 1 − ε`(R4가 R0보다 *느림*) → **이상 신호.** 완전 직렬에서 왕복 2개를 줄인 R4 점유시간은 ≤R0여야 하므로 회귀는
     리팩터가 sub-ms 비용·커넥션 체크아웃 차이를 들였거나 측정 왜곡이라는 뜻 → H_floor '입증'으로 분류 금지, 원인 규명
     전까지 무효 처리.
5. **거울 확인(R3) — 정성 보강만, 정량 반증권 없음:** ε-가드(규칙 2)는 R4 비(ρ*=2, 문턱 1.5)에만 도출됐다. R3를 정량
   분리(ρ_R3=1.33을 r≈1과 가르기)하려면 더 빡센 `ε < (ρ_R3−1)/2 ≈ 0.165`가 필요한데 게이트는 ε<0.5만 보장 →
   ε∈[0.165, 0.5)(게이트 통과 합법 영역)면 지지밴드 `[1−ε, 1+ε]`가 1.33을 삼켜 **같은 결함이 R4→R3로 이전**된다.
   따라서 R3는 **R0·R3·R4 3점의 정성 추세로만** 읽는다(세 점이 *평평*이면 H_floor 보강, *기준비 선을 따라 단조 상승*이면
   H_왕복 보강) — `r_R3→1.33이면 헤드라인 반증` 같은 **정량 반증 단언은 금지**. **R4(유일하게 ε-가드된 정량 시험)가
   정본**이며, R4 판정과 R3 정성 추세가 어긋나면 R4를 따르고 불일치를 관측치로 기록한다. (R3를 정량 반증에 쓰려면 별도로
   `ε < 0.165` 선검사를 통과해야 하고, 미통과면 R3 정량 판정 보류.)

> 이렇게 500-VU 런은 정합 게이트만 찍는 무력한 장치가 아니라 **헤드라인을 반증할 수 있는 채점 장치**가 된다. **단, 이
> 반증가능성은 `ε < 0.5`가 성립할 때만 발동하는 *조건부*다** — 고꼬리 단일핫키 워크로드(p95 2630ms)에서 ε가 그 위면
> `PreRegisteredAdjudicationGate`(M2)가 판정 보류로 빠져 부하 채점이 무력화되고, 그 경우 헤드라인 1차 증거는 **구조
> 카운트 + R3 3점 정성 추세로 정직히 후퇴**하며 부하로는 '못 가름'을 결론으로 기록한다(한계 인정). 사전추정 ε_hi=21.9%로
> 현 단계는 발동 유효(Context); R4 빌드 후 결합 CV로 재확정한다.

**비교 합법성:** R0·R2·R3·R4는 정책(park·503=0)·핫키·부하모델 고정, **변하는 단일 변수 = in-lock 왕복 수**뿐 →
throughput 직접 비교 **합법**(3-3 Step G의 '정책 다른 버전 비교 금지'에 안 걸림; 3-3-2 유한대기 통제 수법 계승).
R1만 풀이라는 제2변수가 변하므로 이 판정에서 **제외**(R1은 자기 진단 규칙으로 따로).

## 실험 사다리 (R0 기준 · 시도 1~4 + 곁가지)

> 각 칸 = 가설 → 예측 → **[프로브 카운트]**(동시성 0, 결정론) + **[부하 실측 후 기입]**(throughput·게이트). 코드 0줄
> 시점이라 실측 슬롯은 비운다. 엔드포인트 `/api/r{n}/coupons/issue`(기존 `/api/v{n}` 미오염). R0는 literal 재사용이
> 아닌 동일 계측 충실 복제.

| 칸 | 무엇 | in-lock 왕복 수 | 한 줄 |
|---|---|---|---|
| **R0** | 현행 v3 (기준선) | **4** | FOR UPDATE SELECT + existsBy SELECT + INSERT + dirty-flush UPDATE coupon |
| **R1** | 시도 1 · 풀 스윕 10→20→30 (진단) | 4 (불변) | 코드 동일, 풀만 변경 |
| **R2** | 시도 2 · 락 밖 군더더기 제거 | 4 (불변) | DB 미접촉 작업만 락 밖으로 (managed Coupon은 그대로) |
| **R3** | 시도 3 · 원자 수축, existsBy 유지 | **3** | bulk `tryConsume` UPDATE — 엔티티 미적재로 dirty-flush UPDATE 소멸 (4→3) |
| **R4** | 시도 4 · existsBy → UNIQUE 백스톱 | **2** | tryConsume UPDATE + INSERT (3→2) |
| **R5** | 곁가지 · 낙관락 @Version | (분석 전용·격리) | 스키마 충돌 + 의미론 비대칭 (아래) |

### R1 — 시도 1 · 풀 스윕 (진단·음성 대조군) ※ 가장 먼저 실행
- **가설:** 풀(의자)을 10→20→30으로 늘리면 throughput이 오른다.
- **예측·판정:** **효과 없음** — throughput 풀에 평평하면 천장=점유시간(H_floor 측 지지). **만약 throughput이 풀에
  비례해 오르면 천장=풀 → 전체 전제 반증**(이 칸도 반증 가능). pending은 200−pool로 *감소*.
- **503=0 제외:** 풀 스윕은 핫 행 X-락 큐 깊이를 ≈pool로 키우는 유일 개입 → pool=30에서 `큐깊이 × holder당 임계구간
  (fsync 포함)` 꼬리가 기본 `innodb_lock_wait_timeout=50s` 초과 시 1205→503 발화 가능. 따라서 **R1에서는 503=0을
  단언하지 않고 503 수를 관측치로 수집**(abort 아님). 503=0 불변은 **코드 동일·풀 비팽창 칸(R0/R2/R3/R4)으로 한정**.
  (대안인 compose `innodb_lock_wait_timeout` 명시 핀은 통제변수 추가라 의도 회피 — §열린 결정에서 재검토.)
- **핀:** 의도 풀값 env 주입, 부팅 assert가 실제 `maximumPoolSize`==주입값 대조.
- **[프로브 카운트]** 4 · **[부하 실측 후 기입]**

### R2 — 시도 2 · 락 밖 군더더기 제거 (`FOR UPDATE`·managed 엔티티 유지)
- **가설:** 락 안 비-DB 작업(사전검증·DTO·응답조립·로깅)을 밖으로 빼면 점유시간이 준다.
- **예측:** **효과 없음(≈0).** 뺀 건 DB 미접촉 sub-ms뿐 → commit floor에 묻힘. 왕복 수 불변(4). throughput은 R0와
  노이즈밴드 안이어야 정상(이 칸은 H_floor의 *대조군* — R2 throughput이 유의하게 오르면 '군더더기'가 실은 sub-ms가
  아니었다는 뜻).
- **단일변수: existsBy는 락 안 유지** + **락 밖으로 빼는 건 DB 미접촉 작업만**(락 밖 별도 tx로 옮기면 커넥션 체크아웃
  2회 → pending 제2변수 오염).
- **필수 — managed Coupon을 existsBy SELECT *앞*에서 건드리지 말 것:** `FlushModeType.AUTO`가 쿼리 전 일관성 위해
  dirty `UPDATE`를 existsBy 직전 **조기 flush** → 그 UPDATE가 커밋 flush와 분리/순서변동되어 R2 카운트가 4 아닌 값으로
  *조용히* 어긋남. R2 리팩터는 응답조립·사전검증을 **엔티티 적재 *전* 또는 커밋 *후*** 구간으로만 옮긴다.
- **[프로브 카운트]** 4 · **[부하 실측 후 기입]**

### R3 — 시도 3 · 원자 수축, existsBy 유지 (단일변수 = 읽고-고치기 합치기)
- **가설:** read-modify-write(SELECT FOR UPDATE→read→UPDATE)를 조건부 UPDATE 한 문장으로 합치면 점유시간이 준다.
  *직관적 주인공.*
- **예측:** 왕복 수 4→3(dirty-flush UPDATE 소멸 + FOR UPDATE SELECT가 조건부 UPDATE로 흡수). **throughput은 사전 등록
  판정에 따라 ≈평평 예상**(commit floor 지배 → 합쳐도 가려짐). **이 칸이 반전: 영웅 기법의 구조적 단축이 throughput엔
  거의 안 나타남을 측정으로 보임** — 단 **R3는 정성 추세점일 뿐 정량 반증권이 없다**(§사전 등록 판정 규칙 5): `r_R3→1.33`을
  정량 반증으로 읽지 않고, R0·R3·R4 3점 추세가 *기준비 선을 따라 단조 상승*이면 H_왕복을 *정성적으로 보강*할 뿐이다.
  정량 반증은 R4가 정본(R3 정량 사용은 별도 `ε<0.165` 선검사 통과 시에만).
- **컴포넌트**(엔티티 미수정, `CouponRepository`에 신규):
  ```java
  @Modifying
  @Query("update Coupon c set c.issued = c.issued + 1 where c.id = :id and c.issued < c.totalQuantity")
  int tryConsume(@Param("id") Long id);   // affected: 1=성공 / 0=소진
  ```
  R3는 `tryConsume` 후에도 **existsBy 중복검사 락 안 유지**(단일변수: 합치기만 격리, 중복검사 위치는 R4 변수).
- **순서 게이트:** R3 로그에 `coupon SELECT==0` 백스톱 + 칸 기대 문 수(3)·순서 게이트.
- **[프로브 카운트]** 3 · **[부하 실측 후 기입]**

### R4 — 시도 4 · existsBy → UNIQUE 백스톱 (단일변수 = 왕복 하나 제거)
- **가설:** 락을 쥔 동안의 *실제 DB 왕복*(existsBy SELECT)을 통째로 없애면 점유시간이 준다.
- **예측:** 왕복 수 3→2. **사전 등록 판정의 주 시험 칸** — `r=throughput(R4)/throughput(R0)`이 `≤1+ε`면 H_floor
  입증, `≥1.5`면 헤드라인 반증. 어느 쪽이든 *발견*.
- **필수 — 에러 계약:** 중복은 이제 `UNIQUE(coupon_id,user_id)` 위반 = MySQL **1062 /
  `DataIntegrityViolationException`** → 분류기(1205만)·핸들러 그대로면 500 'other'로 샘 → **1062→`DuplicateIssueException`
  명시 번역** 추가(또는 분류기 1062 매핑). 500-VU 유니크 userId라 미발화이나 계약은 코드로.
- **[프로브 카운트]** 2 · **[부하 실측 후 기입]**

### R5 — 곁가지 · 낙관락 @Version (분석 전용 · 격리 빌드 필수 · 단일빌드 혼합 금지)
- **가설:** 락을 안 잡고 충돌 시 재시도하면? 단일 핫키 초고경합에서 재시도 폭풍으로 더 나빠질 것.
- **의미론 비대칭(격리 필수 근거):** `@Version`을 공유 `Coupon` 엔티티에 달면 — R0/R2(managed 적재+dirty)는 커밋
  flush가 `UPDATE coupon ... WHERE id=? AND version=?`로 **낙관락化**되지만, R3/R4의 `tryConsume`은 **bulk @Modifying이라
  영속성 컨텍스트를 우회 → `@Version` 자동 증가·검사 안 함**(JPA 명세상 bulk update는 버전 자동관리 밖). 따라서 같은
  빌드에 R5를 섞으면 **R0/R2 버전검사 ON ↔ R3/R4 OFF** 비대칭이 ddl 충돌을 넘어 *조용히* 생겨 baseline 통제변수가
  어긋난다(부팅 assert는 컬럼 존재만 봄, 비대칭 미적발).
- **결론:** **단일 빌드 혼합 금지. R5는 별도 빌드/프로파일 격리에서만, 기본 분석 전용**(왜 핫키에서 불리한가 정성
  논증). 정책 변경(대기→재시도)이라 throughput 직접 비교 재금지 — 분포로만.

## 측정 규율

### M1 — 구조 카운트 = 단일요청 프로브 (결정론·정적)
- **카운트는 포화 런이 아니라 동시성 0 단일요청 프로브 1회 + 코드 정적 카운트로 확정**한다. 포화 인터리브 로그에서
  트랜잭션 경계를 패턴 추론하지 않는다(Hibernate SQL 로깅은 BEGIN/COMMIT 미표시 + closed-loop 연속 처리라 "전체
  문수/요청수" 평균은 인터리브·warmup으로 비정수 오염). 프로브는 모호함 없이 R0=4·R3=3·R4=2.
- **표본:** 카운트는 **성공 트랜잭션 표본**으로만(소진 경로는 R0=2문+롤백, R3=tryConsume affected=0의 1문 → 정확성축
  평균이 표와 불일치). 프로브는 정의상 성공 1건이라 이 오염을 구조적으로 회피.
- **응답 p95로 t·왕복수를 대체 금지**(풀 대기+락 보유+커밋 혼합).

### M2 — 핀 단일 소스 + 부팅 assert + **전 칸 flush 게이트** + 채점 스텝 게이트
- `CriticalSectionPins`(상수): VU(500)·핫키·`HIKARI_MAX_POOL_SIZE`(10)·`TOMCAT_THREADS_MAX`(200)·정책(park)·
  풀 스윕 단계(R1: 10/20/30)·**R0·R3·R4 반복 횟수(노이즈밴드용 각 ≥3)**·사전 등록 문턱 파생식(ρ*·결합-CV ε 산출법).
- `CriticalSectionPinsBootAssert`(`@EventListener(ApplicationReadyEvent)`, **측정 전용 `@Profile` 게이트** — 본체
  무오염) → 실제 풀·threads 대조, 불일치 시 기동 실패.
- **flush/카운트 순서 게이트를 R0~R4 전 칸에 일반화:** 칸별 기대(문 수·순서)로 조기 auto-flush 오염을 전수 적발 —
  R3만 가졌던 백스톱을 R0·R1·R2·R4로 확장(특히 R2 existsBy 앞 managed 접근 금지 검사).
- `innodb_lock_wait_timeout`은 MySQL측 변수 → 앱 assert 불가, `SHOW VARIABLES` 대조 또는 compose 명시(§열린 결정).
- **채점 스텝 게이트 `PreRegisteredAdjudicationGate`(부팅 assert 아님 — ε는 R0·R4 각 ≥3런 *사후* 교차런 집계라
  `ApplicationReadyEvent` 부팅 시점엔 미존재 → 런타임 채점 단계 게이트). 실행 호스트 = 부하 측정 파이프라인의 채점 스텝(앱 외부,
  교차런 throughput 로그 입력)** — Spring 빈/`@EventListener`로 배치 금지(부팅 때 교차런 throughput 미존재로 무발화):
  R0·R4 각 ≥3회 성공 throughput의 결합 CV **신뢰구간 상한 `ε_hi`**(보수적, 규칙 1)를 산출 → `ε_hi ≥ (ρ*−1)/2 = 0.5`면
  r 분류를 **하드 거부**하고 판정 보류(§사전 등록 판정 규칙 2). 점추정이 아닌 `ε_hi`라 소표본 과소추정이 게이트를 조용히
  통과하지 못한다. 부팅 핀이 풀·threads 불일치로 *기동*을 막는 것과 **대칭으로, 이 게이트가 채점 시점에 밴드 비겹침을
  집행**한다 — M5(c)는 이 게이트의 런타임 자가검증이다. (이 게이트 미배선 시 ε-가드는 선언에 머물러 ε≥0.5 런이 조용히
  통과한다.)

### M3 — 부하 모델 = 단일 핫키 초고경합, 정책 고정
- 500 VU 단일 coupon_id 폐루프(3-3 동결 부하). 매 런 전 리셋. 성능축 total 대용량(전건 성공 → throughput·카운트
  성공표본), 정확성축 total=100(매진 신호). **R0·R3·R4 모두 ≥3회 반복**(R0만이 아님 — 비 `r=tput(R4)/tput(R0)`의 실제
  분산은 양변 잡음의 결합이라, R4를 단일런으로 두면 한 잡음 표본이 유일 정량 판정을 좌우한다). ε는 R0 CV 단독이 아니라
  **비의 결합 CV**(R0·R4 양쪽 반복에서, 보수적으로 `ε ≈ √(CV_R0² + CV_R4²)`)로 산출해 R4 노이즈를 밴드에 흡수한다.
- 개루프 도입 여부·동결본 비교 합법성 미결(§열린 결정).

### M4 — baseline 정합
- R0가 현행 v3 동치임을 코드로, R1~R5 신규 경로가 v3 빈 미오염 전수 확인. 프로브 카운트 수단이 점유시간 미증가.
- R4 lost-update 흡수 함정: 원자 UPDATE로 `coupon.issued` 정확해져도 **진실 소스는 `coupon_issue` 행수**.

### M5 — 측정 유효성 게이트 + 자가 검증
- 정확성축은 settle(1~2s) 뒤 행수==100(3-3 F3 graceful-stop 창 방지). 성능축 초과 0.
- 자가 검증 3건: (a) 고의 핀 불일치→abort, (b) 고의 응답-p95-측정 → 개선이 풀 대기에 묻힘을 *드러냄*, (c) **사전 등록
  문턱 자가검증** — R0 두 표본으로 `r≈1`이 노이즈밴드 안에 드는지(문턱 산출식 자체의 건전성) **+ 밴드 비겹침
  `1+ε < 1.5`(ε<0.5)를 `PreRegisteredAdjudicationGate`(M2)가 채점 시점에 집행함을 검증: 고의 ε≥0.5 주입 → 분류 하드
  거부·판정 보류 발화 확인(런타임 게이트지 선언 아님). R3 정량 판정은 `ε<0.165` 미통과 시 보류됨도 함께 검증**.

### M6 — 단정 금지·실측 인용
- 노이즈밴드 ε·관측 r·R5 재시도 분포·각 칸 throughput은 a priori로 박지 말고 실측/동결본/「열린 결정」으로.
  **문턱 1.5는 구조적 카운트비(ρ*=2)에서 *도출*된 결정 경계지 예측 outcome이 아니다** — 이 구분을 스펙이 명시.

## 배선 계약 — 503=0이 코드로 성립하는 조건

신규 `CouponOccupancyController`(R0~R4)는 셋을 **모두** 만족:
1. **`com.project.api.coupon` 패키지 안에 둔다**(`@RestControllerAdvice(basePackages="...coupon")` 커버). 다른
   패키지면 409/503이 전부 500으로 새 → 503=0 거짓 → throughput 비교 합법성 *조용히* 무효.
2. **`issueViaV3`식 분류 경계 복제**(각 R 경로를 `try{...}catch(DataAccessException|TransactionException e){throw
   CouponDbExceptionClassifier.classify(e);}`로, 또는 공통 경계 빈 추출).
3. **R4: 1062→`DuplicateIssueException` 명시 번역**(위 R4).

## 열린 결정 사항
- **엔드포인트 네임스페이스** `/api/r{n}`(기존 `/api/v{n}` 미오염), R0는 literal 재사용이 아닌 동일 계측 충실 복제.
- **R5 `@Version`** — 단일빌드 혼합 금지 확정, 기본 분석 전용, 구현 시 격리 빌드/프로파일 필수(위 R5 의미론 비대칭).
- **핀 값·`innodb_lock_wait_timeout` 검증 방식**(R1 503 관측 vs compose 명시 핀)·**노이즈밴드 반복 횟수** — 파일럿
  동결: n=5·α=0.05·χ² σ-bound 채택, `ε_hi`=21.9%. n은 `ε_hi` CI가 판정에 쓸 만큼 좁아지도록 파일럿 분산에서 도출(≥3은
  하한); R4 빌드 후 결합 CV로 재도출.
- **개루프(constant-arrival-rate) 도입 여부·동결본(폐루프) 비교 합법성.**
- **auto-flush 순서 백스톱**(전 칸 R0~R4)이 조기 flush 오염을 실제로 전수 적발하는지(특히 R2 existsBy 앞 managed 접근).
- **R0→R3 단일변수 주장**(읽고-고치기 합치기만 격리; existsBy 위치변경은 R4 변수).
- **pending은 t·왕복수 불변** — R1에서만 200−pool 보조.
