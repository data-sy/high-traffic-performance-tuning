## 부록 A: 인덱스 대시보드 측정축 교정 — **3-6에서 분리 권고 (별도 작업/PR 후보)**

> **이 절은 3-6 Work Order에 포함하지 않는다.** design-review 1순위 의제 = "이 작업을 3-6에서 떼낼지". 근거는 바로 아래.

**배경 — 코드로 검증된 오진 정정 (이 세션의 실제 성과):** Phase 3-5는 *"`/api/v4/products`가 200을 안 줘서 index 대시보드 v4 시계열이 안 잡힘 → 앱 동작 이슈"* 로 인계했으나, **코드를 직접 까서 확정**한 결과 이는 앱 버그가 아니다.
- ✅ **검증됨:** `grep`상 product 컨트롤러는 `ProductController` 하나, 매핑은 `@GetMapping("/api/v1/products")` 하나뿐. v2/v3/v4 엔드포인트는 **부재**(500이 아니라 존재 자체가 없음). 부재가 phase3-1 설계상 정상("v1~v4 별도 컨트롤러 금지 / before·after 차이는 인덱스 SQL 스왑으로 발생").
- ✅ **검증됨:** `index.json`은 3개 패널에서 `sum by (uri)(...{uri=~"/api/v[0-9]+/products"})`(랭킹 패턴 복사). 인덱스에는 URI가 v1 하나뿐이라 **구조상 영원히 v1 한 계열만 잡힌다.**
- 즉 "v4 미반환"이 아니라 **uri-라벨 분리 전제 자체가 인덱스 시나리오에 부적합**하다. 인덱스의 "버전 축"은 URI가 아니라 *적용된 인덱스 SQL(step1~5)* 이다.

**왜 3-6에서 분리하나 (non-load-bearing polish 디커플):**
- 이 작업은 단순 코드 읽기가 아니라 `index-test.js` 수정 + `index.json` PromQL 교체 + **불확실 PoC(k6 step 태그가 Prometheus 라벨로 보존되는가)** 를 포함하는 **측정 인프라 리팩터**다.
- ⚠ **분리 사유 정정(design-review):** 원래 근거 "단일변수 격리(데이터규모↔측정축)"는 **이제 거의 무효**다. 부록 A 의존 지점(Step B 증거·Step D 캡처·성공기준 #4)이 전부 본류 밖으로 격리돼 있어, **3-6은 before/after를 대시보드로 비교하지 않는다**(인덱스 증거=EXPLAIN+k6 json). confound될 두 변수가 애초에 만나지 않으니 "격리"라는 프레임 자체가 안 맞음. **진짜 사유 = 부록 A의 다계열화는 3-6 결론에 non-load-bearing한 *전시(presentation) polish*라, 헤드라인이 cosmetic 작업을 기다리지 않게 디커플한다**(전시 가치는 별개로 유효 — 포폴 인덱스 딥페이지 시각 자료 용도). [[control-var-match-prior-version]] 규율은 *측정 경로가 실제로 겹칠 때* 적용되는 것이라 여기엔 비해당.
- **인덱스의 진짜 증거는 이미 동작한다** — EXPLAIN(type=ALL+filesort → ref, rows 스캔량) + step별 k6 json. 다계열 대시보드는 본질적으로 polish. PoC 실패 시 폴백("시간범위 분리")은 polish 하나 만들자고 자동화를 깎는 것.
- **권고:** 측정축 교정을 별도 소형 작업/PR로 분리 → 3-6은 "데이터 적재 + ①③ 재측정"에 집중. PoC가 막혀도 스케일업 본류가 멈추지 않는다.

**결정안(승인 시 별도 작업으로):** 단일 컨트롤러 설계 보존 + **k6 step 태그**를 측정축으로 삼아 `index.json`을 **uri-split → step-split**로 수정. (대안 "v2~v4 컨트롤러 신설"은 phase3-1 규칙 위반이라 기각.)

### A-1. k6 인덱스 스크립트에 step 태그 추가 — `test/load/index-test.js`
- **✅ 코드 재확인: 측정 인프라는 이미 존재한다.** `run-ts1-k6.sh`는 매 step 실행 시 이미 `--out experimental-prometheus-rw` + `K6_PROMETHEUS_RW_*` + `--tag step="${step_num}-${step_name}"` + `--summary-export=stepN-*.json`을 **모두** 수행한다. 즉 step 태그가 붙은 k6 메트릭이 **이미 Prometheus로 흘러가고 있다**(신규 작업 아님).
- 따라서 `index-test.js`의 요청별 `__ENV.STEP` 태그는 **불필요/중복**일 가능성이 크다 — run 레벨 `--tag step`이 이미 각 step 실행을 분리하기 때문. (요청 단위 세분이 필요할 때만 추가.)
- **부록 A의 실제 잔여 작업은 A-2 하나** — 흘러들어온 step-태그 k6 메트릭을 대시보드가 *질의*하도록 PromQL을 바꾸는 것.

### A-2. `index.json` 대시보드 PromQL 교정 (부록 A의 핵심·유일 잔여)
- 3개 패널(throughput=`rate(_count)` / latency=`rate(_sum)/rate(_count)` 파생 avg / `max(_max)`)의 `sum by (uri)(http_server_requests_seconds_*{uri=~".../products"})`를
  **k6 메트릭 + `step` 라벨 기반**으로 교체(예: `k6_http_req_duration_p95{step!=""}`를 `by (step)`로). ⚠ 실제 태그값은 `run-ts1-k6.sh`가 `step="1-no-index"`·`"4-composite"` 형태로 붙이므로(`step` 접두사 없음) `step=~"step.+"`는 0건 매칭 — `{step!=""}` 또는 `{step=~".+"}`를 쓴다.
- 서버측 actuator는 uri가 v1 하나라 step 구분이 불가하므로, 인덱스 패널의 다계열 비교는 **k6 클라이언트 메트릭(step 태그)**으로 일원화한다. (랭킹은 uri로 v1~v4가 진짜 갈리므로 actuator 유지 — 시나리오별 소스가 달라도 무방.)
- 패널 설명에 "인덱스 버전 축 = 적용된 인덱스 SQL(step), URI 아님"을 명시.

> ⚠ **차단 조건(완화됨):** "k6 step 태그가 Prometheus 라벨로 보존되는가" PoC는 **기존 `run-ts1-k6.sh` 실행 결과로 이미 검증 가능**할 수 있다(이미 remote-write+태그를 하므로 Prometheus에서 `k6_*{step=...}` 존재만 확인하면 됨). 보존이 제한적이면 대안 = 시간범위 분리/메트릭명 분리. **이 PoC가 어떻든 3-6 본류(Step A~D)는 영향 없음** — 인덱스 증거는 `--summary-export`로 떨어지는 stepN json(파일)으로 이미 확보되기 때문.

## Step A: 데이터 생성 스크립트 스케일업 — 서버사이드 대량 적재

### 문제
현 `scripts/generate-test-data.sh`는 bash `printf` 루프로 INSERT 문자열을 tmpfile에 쌓아 `BATCH_SIZE=5000`행 단위 다중 INSERT로 적재한다(클라이언트사이드 bash 루프가 본질). **1M product / 1.5M order_item을 이 방식으로는 비현실적**(수백 MB tmpfile, 1M+ 회 bash printf 반복으로 수십 분). 또한 `mysql -h127.0.0.1` 직접 접근으로 프로젝트 규칙 위반.

### 설계: bash 루프 → 서버사이드 `INSERT ... SELECT`
모든 행 생성을 MySQL 서버 내부에서 수행해 bash가 데이터를 나르지 않게 한다.

- **접근 함수 교정:** `run_mysql() { docker exec -i docker-mysql-1 mysql -uroot -proot flashdeal "$@"; }` 로 전환(직접 host 접근 제거).
- **파라미터화:** `PRODUCT_COUNT`(기본 1000000)·`ORDER_COUNT`(기본 500000)·`ITEMS_PER_ORDER_MAX`(기본 5) 환경변수. 기존 100K/50K도 같은 스크립트로 재현 가능하게.
  - ⚠ **전제: `ORDER_COUNT`는 5의 배수여야** order_item 정확 1.5M(= `ORDER_COUNT`×3) 불변식이 성립한다 — `1+(id%5)` 5주기 합은 `N%5==0`일 때만 정확히 3N(비배수면 잔여 residue만큼 어긋남). 기본 500000·기존 100K/50K 모두 충족. 비배수 값을 넣으면 아래 적재-후 `COUNT(*)=ORDER_COUNT*3` assert가 잡긴 하나 메시지가 "카운트 불일치"라 원인(5 배수 아님)을 바로 못 읽으므로 전제로 못박는다.
- **tally(numbers) 테이블:** digit 테이블 cross join으로 시퀀스 생성(재귀 CTE는 `cte_max_recursion_depth` 제약 → tally 방식 권장).
  - `seq` = product/orders 행 생성용(개수 N개면 됨 — PK는 AUTO_INCREMENT라 1-base 자동, `n`은 이름/카테고리 산출에만 쓰여 base 무관).
  - **`seq5` = 반드시 `n ∈ {1,2,3,4,5}` (1-base).** ⚠ tally가 0-base(0..)면 `seq5`는 `WHERE n BETWEEN 1 AND 5`로 **명시 필터**한다. 0-base를 그대로 쓰면 order_item 행수가 2~6/주문(평균 4, ~2M)으로 어긋난다 — "정확히 1.5M"은 seq5 1-base에서만 성립.
- **users 시드 (필수 — 누락 시 0행):** orders가 `user_id=FLOOR(RAND()*1000)+1`로 1K users를 전제하므로 **Step A가 users 1K를 먼저 적재**한다(기존 스크립트의 user printf 블록 보존 또는 `INSERT...SELECT FROM seq LIMIT 1000`). Order→User는 `NO_CONSTRAINT`라 댕글링 user_id가 즉시 실패는 아니지만, "users 1K" 전제·서사를 지키려면 시드 필수.
- **product 적재:** `INSERT INTO product (name, price, category, stock, sales_cnt, created_at) SELECT CONCAT(cat,' 상품 ',n), ..., cat, ..., 0, NOW() FROM seq` — 카테고리는 `ELT((n % 5)+1, '전자기기','의류','식품','도서','스포츠')`, price/stock은 `FLOOR(RAND()*...)`.
  - **created_at 분포(결정론):** 전부 `NOW()`면 created_at 정렬이 무의미해 인덱스 시나리오(ORDER BY created_at) 변별이 약해진다. **과거~현재로 분산하되 `RAND()`가 아니라 PK의 결정론 함수로** 뿌린다(예: `NOW() - INTERVAL (n % 365) DAY`, `n`=seq 시퀀스). order_item의 seq5 결정론 규율과 동일. ⚠ **RAND 사용 규율(내적 일관):** RAND를 **(a) JOIN 카디널리티/행수**와 **(b) 측정 정렬축(created_at)** 엔 금지하되, `product_id`·`quantity`·`price`·`user_id` 같은 **행별 독립 스칼라 값엔 허용**한다. 따라서 이 규율이 보장하는 건 "**재현 가능한 구조·측정속성**"(행수·정렬 분포·EXPLAIN 형태)이지 *비트-동일 데이터셋*이 아니다 — 값 컬럼과 `NOW()` 기준점은 런마다 달라진다(매 적재 top-100 내용도 달라짐). created_at의 `RAND()` 날짜는 정렬축 (b)를 흔들어 측정 변별을 깨므로 금지. (n%365는 365개 일자에 균등 순환 → 정렬·복합인덱스 변별 충분.) ⚠ **커플링 주의(design-review Note ⑱):** category(`n%5`)와 created_at(`n%365`)이 같은 `n`의 결정론 함수라, 질의 대상 단일 카테고리(예 '전자기기' = `n≡0 mod5`) 내부에선 created_at이 **73종 일자**(5의 배수 mod365)로 축소된다(전체 365가 카테고리 내부에서 그대로 유지되지 않음). 인덱스 데모(filesort↔ref 대비, type/rows)에는 **무영향**이므로 무수정 가능 — "365 균등"은 전역 기준이며 카테고리 내부 다양성은 73임만 인지한다. *(검증: phase3-1 EXPLAIN이 filesort/ref 차이를 보이는지)*
- **orders 적재:** `INSERT ... SELECT FROM seq` (user_id=`FLOOR(RAND()*1000)+1`, status=`ELT(...)`, total=0, created_at는 위와 동일하게 **결정론 분산** `NOW() - INTERVAL (n % 365) DAY`).
- **order_item 적재 (가변 개수 — 결정론적 패턴 확정):** orders × (1~ITEMS_PER_ORDER_MAX). 주의: `1+FLOOR(RAND()*5)`의 *범위 자체는 1~5로 정상*(RAND[0,1)→FLOOR→0~4→+1). 진짜 문제는 범위가 아니라 **`RAND()`를 JOIN ON 절에 넣을 때의 비결정성** — 옵티마이저가 행마다 일관되게 평가하리란 보장이 약해 분포·재현성이 깨진다. ✅ **확정 패턴:** 행 수를 RAND 없이 결정론으로 고정한다 —
  ```sql
  -- ⚠ order_item에는 created_at 컬럼이 없다(OrderItem 엔티티에 @CreatedDate 필드 부재).
  --   created_at을 넣으면 Unknown column으로 즉시 실패 → 컬럼 자체를 넣지 않는다.
  -- ⚠ PRODUCT_COUNT는 MySQL 유저변수(@PRODUCT_COUNT)가 아니라 bash 리터럴(${PRODUCT_COUNT})로 주입한다.
  --   유저변수는 커넥션 로컬 → 청크마다 run_mysql(=docker exec=새 커넥션)을 돌리면 다음 청크에서 NULL이 되고,
  --   product_id=NULL이 조용히 적재된다(@JoinColumn 기본 nullable, 적재-전 assert도 못 잡음).
  --   → 리터럴 보간으로 못박거나, 부득이 유저변수면 청크 SQL마다 SET @PRODUCT_COUNT=... 를 동봉.
  INSERT INTO order_item (order_id, product_id, quantity, price)
  SELECT o.id,
         FLOOR(RAND()*${PRODUCT_COUNT})+1,       -- product_id (행별 스칼라, 범위 1..PRODUCT_COUNT — 분포 보장 불필요)
         FLOOR(RAND()*5)+1,                      -- quantity 1~5
         FLOOR(RAND()*90000)+10000               -- price
  FROM orders o
  JOIN seq5 s ON s.n <= 1 + (o.id % 5);          -- seq5.n ∈ {1..5}(1-base) → 행 수 = 1~5 결정론, 평균 3
  ```
  - **`created_at` 분산은 `product`·`orders`에만 적용**(둘만 createdAt 보유). `order_item`은 created_at 자체가 없고 측정에도 불필요(랭킹=SUM(quantity), 인덱스=product 기준).
  - 행 수 게이트(`o.id % 5`)는 결정론이라 **정확히 1~5, 평균 정확히 3** 보장(RAND-in-join 비결정성 회피 + 재현성). **단 seq5가 1-base일 때만**(위 tally 주의 참조). 보너스: `id % 5`가 1..ORDER_COUNT에 균등 순환하므로 order_item이 **정확히 ORDER_COUNT×3(= 500K×3 = 1.5M, 근사 아님)**. product_id/quantity의 RAND는 행별 독립 스칼라라 분포 정밀도 불필요 — 그대로 사용.
  - **assert(차단) — 적재-전, 두 컬럼 모두:** 정확 1.5M 불변식·무공백 product_id가 각각 **`orders.id` 1..ORDER_COUNT 연속**과 **product PK 1..PRODUCT_COUNT 연속**에 기댄다(전자=`1+(o.id%5)` 합이 정확히 ORDER_COUNT×3, 후자=댕글링 product_id 방지). fresh AUTO_INCREMENT면 둘 다 성립하나 *불변식이 기대는 컬럼에 가드가 있어야* 하므로, order_item 적재 **전에** 두 테이블 모두 `MIN(id)=1 AND MAX(id)=COUNT(*)=목표값`을 검사해 불일치 시 abort. [[dryrun-pin-runtime-assert]]
  - **assert(차단) — 적재-후, order_item 자체:** 적재-전 가드는 부모 PK 연속성만 보고 *생성된 행수·product_id 유효성은 못 본다*. order_item 적재 **직후** 아래를 in-script로 검사해 불일치 시 abort(사람 검증 'Step A 검증' 절에 의존 금지) —
    - `COUNT(*) = ORDER_COUNT*3` (정확 1.5M 불변식의 **직접** 가드 — seq5 0-base 누수·orders.id 불연속을 한 번에 흡수). ⚠ 이 assert가 실패하면 **첫 점검 = `ORDER_COUNT % 5 == 0`인지**(위 파라미터화 전제) — `1+(id%5)` 합은 `N%5==0`일 때만 정확히 3N이라, 5 비배수가 흔한 오작동 원인이다. 가능하면 abort 메시지에 이 힌트를 동봉.
    - `SUM(product_id IS NULL) = 0` AND `MIN(product_id) >= 1 AND MAX(product_id) <= PRODUCT_COUNT` (유저변수 NULL·범위이탈 방지 — 위 SQL 주의의 런타임 가드).
- **청크 적재(중요):** 1.5M을 단일 트랜잭션으로 넣으면 undo log·binlog 폭증 + 거대 트랜잭션이 `innodb_lock_wait_timeout=50s`(핀된 값)를 건드릴 위험. **range 청크 5만~10만 행/커밋으로 분할 커밋**(이 크기는 튜닝 노브 — 너무 크면 위 위험, 너무 작으면 느림). bash는 청크 경계만 돌리고 각 청크는 서버사이드 `INSERT...SELECT WHERE n BETWEEN ...`.
- **집계 갱신:** `sales_cnt`·`orders.total`은 상관 서브쿼리(행마다 스캔) 대신 **GROUP BY + JOIN 일괄 갱신**:
  ```sql
  UPDATE product p
  JOIN (SELECT product_id, SUM(quantity) s FROM order_item GROUP BY product_id) t
    ON p.id = t.product_id
  SET p.sales_cnt = t.s;
  ```
  - ⚠ **이 집계 UPDATE는 청크 규율의 예외(단발 대용량).** 최대 1M product 행을 단일 트랜잭션으로 갱신 + 서브쿼리가 1.5M order_item을 (product_id 보조 인덱스가 아직 없는 상태에서) `GROUP BY` temp로 스캔한다 → INSERT에서 청크로 피한 undo·실행시간 부담을 여기서 재현. dev 머신에선 보통 수 초~수십 초로 완료되나, 느리거나 undo가 부담되면 product PK range로 **청크 갱신**으로 전환(또는 "의도적 단발"임을 적재 로그에 명시). `orders.total` 일괄 갱신도 동일.
  - ⚠ **장식 컬럼 가드(design-review Caution ⑭ — 중요):** `sales_cnt`·`orders.total`은 **3-6의 어떤 측정도 읽지 않는다** — 랭킹 v1은 `SUM(quantity)`를 **라이브 계산**(Step C 대상 정의)하고, 인덱스 시나리오는 `category`+`created_at`만 본다. 즉 **청크 규율을 깨는 유일한 고위험 연산이 비핵심(전시·현실성용) 컬럼을 채운다**. 따라서 이 집계 UPDATE는 (a) product/orders PK range로 **청크화**하거나, (b) 적재 **맨 마지막에 non-fatal로** 돌려(`set -e` 하에서도 실패가 Step A 전체를 abort하지 않게 — 예: 서브셸+`|| echo "[warn] aggregate skipped"`) **느리거나 실패해도 측정 목표(적재 검증·재측정)를 막지 못하게** 한다. 핵심 불변식(행수·product_id 유효성)은 위 assert가 이미 보증하므로 이 컬럼 실패는 비치명적이다.
- **인덱스 타이밍:** 베이스 테이블은 `validate`로 PK만 존재 → 대량 적재가 빠르다. 인덱스 시나리오의 보조 인덱스는 `scripts/index/stepN`이 측정 시점에 생성/삭제하므로 **적재 단계에서 보조 인덱스를 만들지 않는다.**
- **TRUNCATE/FK 순서:** OrderItem의 `order_id`·`product_id` `@JoinColumn`이 둘 다 `ConstraintMode.NO_CONSTRAINT` → **실제 FK 제약 없음 확정. TRUNCATE·적재 순서 무관.** 현 스크립트의 `SET FOREIGN_KEY_CHECKS=0/1`은 방어적 유지로 충분(순서 의존 없음).

### 현실성 설계 (스펙이 명시할 것)
- **예상 시간:** 서버사이드 `INSERT...SELECT` + 청크로 1M+1.5M ≈ 수 분(머신·buffer pool 의존). 실측치는 적재 로그에 기록.
- **예상 디스크:** product 1M + order_item 1.5M + 인덱스 빌드 ≈ 수백 MB. `mysql-data` 볼륨 여유 확인 절차 포함.
- **검증 쿼리:** 적재 후 행 수·카테고리 분포·`sales_cnt` 합 일치 확인(현 스크립트의 Verification 블록 확장).

## Step B: 시나리오 ① 인덱스 재측정 (1M product)

기존 자동화 그대로 재사용. **부록 A(대시보드 교정)에 의존하지 않는다** — 인덱스 증거는 EXPLAIN + step별 k6 json(파일)으로 자족한다. 코드/SQL 신규 없음(스크립트 인자만).
- **헤드라인 = 동일 1M 런 내부의 step1 ≫ step4**(동시점·동인프라 → confound 없음): step1 type=ALL+filesort(~1M 스캔) vs step4 type=ref+no-filesort. **100K 대비 "더 선명"은 EXPLAIN rows 스캔량(인프라 불변)으로 정량**, k6 p95의 cross-scale 대비는 인프라 핀 동일성 확인 시에만(아래 '교차 스케일 confounder' 규율). 랭킹 Step C의 within-scale 헤드라인과 대칭.

- **EXPLAIN(주 증거):** `scripts/measure/run-ts1-explain.sh`의 기본 출력은 `results/explain/`(현재 미존재 = 스크래치). 100K EXPLAIN 베이스라인은 다른 경로(`results/phase3-1-index-optimization/explain/`)라 **재실행해도 베이스라인은 안전**. 1M 결과를 `results/phase3-6-scale-up/explain/stepN-*.{txt,json}`로 분리 보관(스크립트 출력 경로 파라미터화 또는 실행 후 복사).
  - 대상 쿼리 `WHERE category='전자기기' ORDER BY created_at DESC LIMIT 20` — 1M에서 step1(no index, type=ALL+filesort) vs step4(composite, type=ref, no filesort) 대비가 100K 때보다 선명해야 함.
  - **주의:** 1M에서 `CREATE INDEX`는 step마다 수 초~수십 초 소요 → 자동화는 동작하되 전체 실행 시간 증가. 스크립트 타임아웃 없음 확인.
- **k6(주 증거):** `run-ts1-k6.sh` 실행 → step별 `stepN-*.json`(`--summary-export`)을 `results/phase3-6-scale-up/k6/`로 보관. step1 vs step4 p95 차이가 **파일**로 확보됨. (이 스크립트는 부수적으로 remote-write+step 태그도 항상 수행하지만, 본류 증거는 json 파일 — 대시보드 다계열 표시는 부록 A의 PromQL 교체가 있어야 보임.)
- **⚠ 부하 모델 명시(측정 타당성 — 빌드 전 핀):** k6 **VU·duration·ramp를 스펙에 못박는다**(기존 100K/150K용 값을 검증 없이 재사용 금지). step1(무인덱스, 1M 풀스캔+filesort/req)을 과도한 VU로 때리면 Hikari 풀(`maximumPoolSize`)·statement timeout에 걸려 **측정 p95가 쿼리 지연이 아니라 큐 대기·타임아웃 아티팩트**가 된다(같은 503/지연이라도 원인이 "쿼리 비용"이 아니라 "풀 포화"). → 실행 시 step1의 **에러율·풀 포화 여부를 점검**해 풀-바운드가 아님을 확인하거나, 포화분이 섞였음을 결과에 명시. **비포화 판정의 구체 신호(design-review Note ⑯):** ① k6 `http_req_failed` ≈ 0, ② 런 중 Hikari active connections < `maximumPoolSize`, ③ 앱 로그에 statement-timeout 0건 — 셋 다 충족해야 "비포화"로 본다(막연한 "점검" 금지). within-scale step1≫step4 상대격차는 경미 포화엔 생존하나, **절대/ cross-scale p95는 이 셋이 충족될 때만 해석**한다. 같은 1M 런 내 step1↔step4는 동일 부하라 정성 비교는 유효하나 **절대 p95의 의미가 부하 모델에 의존**. (주의: 이 절은 "핀하라"는 *지시*이고 **구체 VU·duration 숫자는 구현 시점에 고른다** — 스펙이 숫자를 미리 주지 않는다. 실패 모드를 막는 진짜 가드는 *비포화 점검*이므로 숫자 부재 자체는 blocker가 아니나, step1 비포화 확인은 **필수**.)
- **⚠ buffer pool warm/cold confound:** step을 순차 실행하면 앞 step(특히 step1 풀스캔)이 buffer pool을 데워 뒤 step이 캐시 이득을 본다 → k6 **절대값** 크기에 캐시 영향. 단 **정성 결론(filesort→ref)은 EXPLAIN으로 캐시-불변하게 확보**되므로 주증거는 EXPLAIN, k6 절대값은 보조로 해석(필요 시 step별 동일 워밍업).
- **before/after 출처:** 인덱스 100K↔1M 대비는 **저장 파일(EXPLAIN rows·k6 json)** 로 한다 — Grafana 대시보드가 아님. (구 `index.json`은 1계열뿐이라 비교할 "before" 샷이 없고, 다계열 대시보드는 부록 A 분리 작업의 산출물.)
- **⚠ 교차 스케일 confounder(단일변수 규율):** 같은 1M 런 안의 **step1↔step4 비교는 confound 없음**(동일 시점·인프라). 그러나 **100K 저장파일 ↔ 1M fresh 런의 k6 레이턴시 교차 비교는 시점이 분리**돼 있어, 100K 기준선이 1M 런과 동일한 쿼리·인프라 핀(Hikari/Tomcat 풀, lock/statement timeout 등)에서 측정됐는지 확인되지 않으면 비교 불가. **원칙: 교차 스케일 대비는 `EXPLAIN` 구조(type/rows/Extra)로 — 인프라 핀에서 자유로움. k6 수치 교차 비교는 핀 동일성이 확인될 때만.** [[control-var-match-prior-version]]
- **(부록 A 완료 시에만)** step 태그·remote-write로 `index.json` 다계열 캡처를 *추가* polish로 붙일 수 있으나 3-6 성공 기준 아님.

## Step C: 시나리오 ③ 랭킹 재측정 (1.5M order_item)

- **대상:** v1(DB `GROUP BY product_id ORDER BY SUM(quantity)` 풀스캔) vs v4(Redis Sorted Set). 킥오프 범위대로 v1↔v4 대비에 집중(v2 인덱스·v3 String도 자동화에 포함돼 있으면 함께 기록).
- **⚠ v2 인덱스 생성 시간(Step B와 대칭):** `run-ts2-k6.sh`의 v2 pre-cmd는 `CREATE INDEX idx_orderitem_product_quantity ON order_item(product_id, quantity)`를 실행한다 — 1.5M order_item에서 수 초~수십 초 소요. 자동화는 동작하되 전체 시간 증가(타임아웃 없음 확인).
- **앱 재기동 필수:** `RankingInitializer`가 부팅 시 DB top-100을 Redis ZSet에 적재 → **데이터 재적재 후 앱을 재시작**해야 v4가 새 데이터를 반영. (재시작 안 하면 v4가 옛 랭킹을 보는 함정.)
  - ⚠ **부팅 비용 가드(design-review Caution ⑮):** 이 재시작 시점엔 `idx_orderitem_product_quantity`가 **아직 없다**(`run-ts2-k6.sh`의 v2 pre-cmd가 측정 중 생성). RankingInitializer의 top-100 적재 쿼리(`GROUP BY SUM(quantity)`)가 **무인덱스 1.5M 풀스캔**으로 돌아 부팅이 수십 초 지연될 수 있고, 헬스체크/운영자가 이를 행으로 오인하면 재시작이 실패로 보인다. → **재시작 전에 `idx_orderitem_product_quantity`를 선생성**(어차피 v2 측정에서 만들어지는 인덱스라 측정 결과에 무영향)하거나, **예상 부팅 지연을 적재 로그·콘솔에 명시**해 정상 지연임을 구분한다.
- **측정:** `scripts/measure/run-ts2-k6.sh`(랭킹 v1~v4 자동화, `test/load/ranking-test.js` 사용) 실행. ⚠ 이 스크립트는 **remote-write를 하지 않고 `--summary-export`로만 저장**한다 — 그래도 `ranking.json`은 **서버 actuator 메트릭**(`http_server_requests_seconds_*{uri=~"/api/v[0-9]+/rankings"}`)을 Prometheus가 스크레이프해 채우므로, **부하만 주면 v1~v4가 uri로 자동 적재**된다(k6 remote-write 불요). 출력 json은 `results/phase3-2-ranking-optimization/k6`에 고정 저장된다(신규 파일명 `v1-no-index.json`… vs 기존 100K 베이스라인 `phase3-2-v1.json`… → **파일명이 달라 비충돌, 100K는 이미 보존됨**). 실행 후 `results/phase3-6-scale-up/k6/`로 **복사는 1.5M 결과 분리·정리 목적**.
  - **헤드라인 = 동일 1.5M 런 내부의 v1 ≫ v4 절대 격차**(동시점·동인프라 → confound 없음). v1 GROUP BY 1.5M 풀스캔 지연 vs v4(ZSet 조회) 평탄. ⚠ **"150K 대비 확대"는 부차 정성 프레이밍으로만** — 랭킹은 인덱스의 EXPLAIN 같은 인프라-불변 구조 증거가 없어 **k6 p95가 유일 증거**라, 150K 저장 베이스라인과의 cross-scale 정량 델타는 인프라 핀(Hikari/timeout/머신/Redis 버전) 동일성이 확인될 때만 쓴다(Step B '교차 스케일 confounder' 핀 규율을 Step C에도 동일 적용, [[control-var-match-prior-version]]).
  - **부하 모델은 Step B와 동일하게 명시·점검**: v1 1.5M 풀스캔이 풀-바운드로 포화하면 p95가 큐 아티팩트가 되므로 VU·duration 핀 + 에러율/풀 포화 확인(값은 구현 시점 결정, v1 비포화 확인 필수). ⚠ **랭킹 대시보드(성공기준 #4)는 actuator `rate()` 패널**이라, 버전별 부하 **duration이 Prometheus `scrape_interval`보다 짧으면 윈도우에 샘플이 1개만 들어가 `rate()`가 빈 패널/0**이 된다(인덱스는 summary-export 파일이라 무관하지만 랭킹 캡처는 여기 의존). → **버전별 duration ≥ 2~3×`scrape_interval`**을 핀해 v4 계열이 빈 패널이 되지 않게 한다.
- **메모리:** `scripts/measure/run-ts2-v4-memory-check.sh`로 ZCARD ≤ 100 유지 확인.

## Step D: before/after 캡처 + 결과 갱신

- **인덱스 before/after:** **저장 파일**로 한다 — `results/phase3-6-scale-up/explain/`(step1 ALL+filesort ↔ step4 ref, rows 스캔량) + `k6/`(step1↔step4 p95). 대시보드 캡처는 부록 A(분리 작업) 완료 시에만 추가.
- **랭킹 before/after:** `ranking` 대시보드(v1~v4 uri로 진짜 분리되므로 교정 불필요)에서 v1 DB ↔ v4 Redis 스크린샷 → `results/phase3-6-scale-up/screenshots/`.
  - ⚠ **통계량 분리(design-review Note ⑰):** `ranking.json` actuator 패널은 **avg(`rate(_sum)/rate(_count)`)·max**를 보이는 반면 정량 헤드라인은 k6 **p95**다 → 스샷은 헤드라인과 *다른 통계량*. 캡션에서 "avg-latency 데모"로 명시하고, 정량 결론은 k6 p95 json 출처임을 분리한다("p95 결과"로 오해 금지).
  - ⚠ **이 스샷은 레이턴시 데모다**(v1 1.5M 풀스캔 지연 ↔ v4 ZSet 평탄). product_id가 1M에 균등 분포(주문당 평균 1.5개)라 SUM(quantity) **top-100 *내용*은 거의 동률 난수 집합** — 포폴에서 "의미 있는 인기 상품 랭킹"으로 전시하면 overclaim이다(레이턴시 데모지 랭킹-품질 데모가 아님). v1≫v4 레이턴시 헤드라인은 분포와 무관하므로 영향 없음. 진짜 인기-편중 랭킹이 필요하면 product_id를 편중 분포(예: Zipf)로 생성해야 하나 **이 작업 범위 밖**.
- **수치 갱신:** `results/phase3-6-scale-up/`에 EXPLAIN·k6·스크린샷 정리. 정본 `results/phase3-1-*`·`phase3-2-*`는 그대로 둠. ⚠ **`run-ts1-k6.sh`는 출력 디렉터리 파라미터화(또는 사전 백업) 후 실행** — `results/k6`의 100K 작업본을 즉시 덮어쓰므로 copy-after로는 못 막는다(위 Context 처방).
- **환경 기록:** `results/phase3-6-scale-up/environment.md`(머신·버전·적재 규모·일자).

## 범위 밖 (선긋기)
- **시나리오 ④ 동시성(쿠폰 100장 동시발급)** — 스케일 무관(동시 *요청 수*에 의존, 데이터 규모 아님). 이 작업 대상 아님(사용자 확인).
- **concurrency 503 분해 패널 실데이터 캡처**(Phase 3-5 후속 백로그) — 동시성 맥락, 여기 아님.
- **N+1(시나리오 ②) 코드** — Phase 3-7로 **분리**. v1~v4(LAZY→EAGER→@BatchSize→Fetch Join) 컨트롤러·Fetch Join 구현이 미작성이라 이 측정 스펙에 넣으면 코딩 스펙으로 비대해짐. **단, order_item을 이번에 최종 규모(1.5M)로 적재**해 3-7 토대를 깐다. ⚠ **"재적재 없이"를 하드커밋하지 않는다** — N+1 통증은 부모→자식 fan-out이 클수록 선명한데 현 분포는 주문당 최대 5개로 얌전하고, 3-6이 남긴 인덱스(`idx_orderitem_product_quantity` 등) baseline도 N+1 시연에 맞지 않을 수 있다. **3-7 설계 시 분포·인덱스 상태가 N+1 데모에 충분한지 재확인, 부족하면 재적재.** 3-7 착수 시 `specs/phase3/phase3-7-n-plus-one.md` 별도 작성.

## 성공 기준
1. `product` 1M · `orders` 500K · `order_item` 1.5M(정확) · `users` 1K 적재 완료(검증 쿼리 일치), `ddl-auto: validate` 무변경, 스키마 불변.
2. 인덱스 ① EXPLAIN/k6 재측정: **헤드라인 = 동일 1M 런 내부 step1 ≫ step4 절대격차**(confound 없음, type=ALL+filesort vs type=ref). 100K 대비 "더 선명"은 **EXPLAIN rows 스캔량(인프라 불변)으로 정량**, k6 p95 cross-scale은 인프라 핀 동일성 확인 시에만(Step B '교차 스케일 confounder' 규율). — **저장 파일**로 입증(대시보드 무관). [랭킹 #3과 대칭 — cross-scale p95를 합격식에 직접 박지 않는다.]
3. 랭킹 ③ v1↔v4 재측정: **동일 1.5M 런 내부에서 v1 ≫ v4 절대 격차**(헤드라인, confound 없음). 150K 대비 "확대"는 인프라 핀 동일성 확인 시에만 정량으로, 아니면 정성 프레이밍.
4. 랭킹 `ranking` 대시보드 v1↔v4 before/after 캡처가 `results/phase3-6-scale-up/`에 존재. (인덱스 다계열 대시보드는 부록 A 분리 작업으로 이관 — 3-6 성공 기준 아님.)
5. 동시성·N+1 코드는 손대지 않음. N+1용 데이터(1.5M)는 적재 완료(단 3-7이 그대로 쓸지는 3-7 설계 시 재확인 — 위 범위 밖 절).

## design-review 의제 (해소됨 — 3차 수렴, Blocker 0. 아래는 검토 이력)
1. **[코드 사실 — 이미 검증됨]** ProductController = `/api/v1/products` 단일, index.json = `sum by (uri)` 3패널. ✅ 이 세션 `grep`으로 확정. 리뷰어는 재확인만.
2. **[가장 중요 — 부록 A 분리 여부 + 범위 재산정]** ⚠ audit로 전제 변화: `run-ts1-k6.sh`는 step 태그·remote-write·summary-export를 **이미 모두 수행** → 부록 A의 실제 잔여 작업은 `index.json` PromQL 교체 **하나**로 축소(신규 스크립트 작업 거의 없음). 그래도 분리 권고는 유지(사유는 **non-load-bearing polish 디커플**로 정정 — "단일변수 격리" 프레임은 의존 지점이 본류 밖이라 무효, 본문 부록 A 참조). **분리 완결성(하류 전파) 점검:** 인덱스 다계열 대시보드는 부록 A 의존 — Step B 검증(json 파일로 닫힘)·Step D 인덱스 캡처(EXPLAIN+k6 json)·성공기준 #4(인덱스 대시보드 제외)까지 일관 확인. 작아진 만큼 "그냥 3-6에 포함" 의견도 검토 가능.
3. **[부록 A 차단조건 — 사실상 해소 가능성]** "k6 step 태그가 Prometheus 라벨로 보존되나" PoC는 **기존 `run-ts1-k6.sh` 실행 결과로 즉시 확인 가능**(이미 remote-write+태그 수행 → Prometheus에서 `k6_*{step=...}` 존재만 보면 됨). 리뷰에서 1분 확인 권장. **3-6 본류와 무관**.
4. **[order_item 가변 개수 SQL — 수정 반영됨]** `JOIN seq5 ON s.n <= 1+(o.id%5)` 결정론 패턴. 근거는 "1~6 off-by-one"이 아니라(`1+FLOOR(RAND()*5)`는 1~5로 정상) **RAND-in-join 비결정성 회피 + 재현성 + 정확히 1.5M**. ⚠ **"정확히 1.5M"은 `seq5`가 1-base(n∈{1..5})일 때만 성립** — tally 0-base면 행수 2~6/주문(~2M)으로 어긋남, 스펙에 `WHERE n BETWEEN 1 AND 5` 핀함. product PK 1..N 연속성 assert도 추가. 리뷰어는 base 핀·패턴 타당성 확인.
5. **[스크립트 이름 — 교정 반영됨]** 측정 자동화 실제 파일명은 `run-ts1-explain.sh`/`run-ts1-k6.sh`/`run-ts2-k6.sh`/`run-ts2-v4-memory-check.sh`(phase3-1/3-2 스펙의 옛 이름 `run-explain.sh` 등과 다름). 출력 경로 하드코딩 → 100K 결과 보존 위해 복사/파라미터화. 리뷰어는 이름·경로 재확인.
- **데이터 분포:** `created_at` 분산 범위(예: 1년)와 카테고리 균등 분포가 인덱스 변별·랭킹 편차에 충분한지.
- **적재 시간 현실성:** 서버사이드+청크가 목표 머신에서 실제 수 분대인지(아니면 청크 크기·`innodb_buffer_pool_size` 튜닝 명시).
- **결과 디렉터리 컨벤션:** `results/phase3-6-scale-up/` 신설 권장(100K↔1M 대비 보존). before/after 출처 = 저장 파일(EXPLAIN/k6), 인덱스는 대시보드 아님.
